## 1. Onset detection in open code (spectral flux, SuperFlux, complex domain, HFC; adaptive thresholding / peak picking; per-band detection) — formulas, defaults, latency, licences

### Takeaway
Every open library uses the same three-stage shape — (a) log-compressed magnitude spectrum on a log-frequency (≈24 bands/octave) filterbank, (b) half-wave-rectified difference to a frame 5–10 ms earlier (SuperFlux adds a 3-bin maximum filter on the reference frame so vibrato does not fire), (c) a causal peak picker "local max over the last 30 ms AND above the moving mean of the last 100–150 ms + δ, with ≥30 ms between onsets" — and with a 1024–2048 window at a 5 ms hop the causal latency is ≈15–30 ms. aubio and BTrack (GPL-3.0-or-later), librosa (ISC), madmom source (BSD-2-Clause) and Meyda (MIT) can be ported into a GPL-3.0-or-later app; essentia, sms-tools and audioMotion-analyzer are AGPL-3.0 (formulas only) and MIRtoolbox is GPL-2.0-only (formulas only).

#### 1.1 aubio (GPL-3.0-or-later) — [SRC] unless marked
- Pipeline (`aubio_onset_do`): STFT → optional adaptive whitening → optional log compression `|X_j| ← ln(λ·|X_j| + 1)` → detection function → peak picker → silence gate → minimum inter-onset interval. — [onset.c L56-L106](https://github.com/aubio/aubio/blob/ad5cf97/src/onset/onset.c#L56-L106); log-mag [cvec.c L158-L169](https://github.com/aubio/aubio/blob/ad5cf97/src/cvec.c#L158-L169)
- Defaults: threshold 0.3; delay 4.3×hop (subtracted from the reported time); minioi 50 ms; silence −70 dB; whitening off; compression off. Per method: **hfc (= "default")** threshold 0.058, λ = 1. **complex** delay 4.6×hop, threshold 0.15, whitening on, λ = 1. **specflux** threshold 0.18, whitening on (relax time 100 s, floor 1.0), λ = 10. **mkl** thr 0.05, whitening, λ = 0.02. **kl** thr 0.35, whitening, λ = 0.02. — [onset.c L283-L338](https://github.com/aubio/aubio/blob/ad5cf97/src/onset/onset.c#L283-L338)
- Command-line sizes: onset buf 512 / hop 256; pitch buf 2048; beat & tempo buf 1024 / hop 512. — [cmd.py](https://github.com/aubio/aubio/blob/ad5cf97/python/lib/aubio/cmd.py#L47-L193)
- Detection functions (j = bin, |X| magnitude, φ phase) — [specdesc.c](https://github.com/aubio/aubio/blob/ad5cf97/src/spectral/specdesc.c#L90-L240):
  - energy `Σ|X_j|²`; **HFC** `Σ (j+1)·|X_j|`
  - **complex domain** `Σ sqrt(| r_prev² + r² − 2·r_prev·r·cos(φ_pred − φ) |)`, `φ_pred = 2θ₁ − θ₂` (phase extrapolated from the two previous frames)
  - phase deviation `unwrap(φ − 2θ₁ + θ₂)` for bins above a magnitude threshold, histogram-weighted mean; "wphase" multiplies by |X|
  - specdiff `sqrt(| |X|² − |X_prev|² |)`, histogram mean
  - KL `Σ |X_j|·ln(1 + |X_j|/(|X_prev,j| + 0.1))`; modified KL `Σ ln(1 + |X_j|/(|X_prev,j| + 0.1))`
  - **spectral flux** `Σ max(0, |X_j| − |X_prev,j|)` (half-wave rectified, L1)
- Adaptive whitening (per bin running peak): `peak_i ← max(|X_i|, max(r·peak_i, floor))`, `|X_i| ← |X_i|/peak_i`, `r = 0.001^((hop/sr)/relax_time)`; defaults relax 250 s, floor 1e-4. — [awhitening.c](https://github.com/aubio/aubio/blob/ad5cf97/src/spectral/awhitening.c#L27-L88)
- Real-time peak picker: 7-value buffer of the detection function (5 past, the tested frame, 1 newer); zero-phase low-pass (biquad b = 0.15998789, 0.31997577, 0.15998789; a₁ = 0.23484048, a₂ = 0, forward-backward); `thresholded = df[tested] − median(buffer) − threshold·mean(buffer)`; peak iff the middle of the last three thresholded values exceeds both neighbours and 0; sub-frame time by parabola `pos + 0.5·(s0 − s2)/(s0 − 2s1 + s2)`. — [peakpicker.c L92-L187](https://github.com/aubio/aubio/blob/ad5cf97/src/onset/peakpicker.c#L92-L187), [mathutils.c L486-L517](https://github.com/aubio/aubio/blob/ad5cf97/src/mathutils.c#L486-L517)
- [CALC] aubio latency: decision 2 hops after the detection-function maximum (1 newer frame in the buffer + 1 for the 3-point test). 44.1 kHz, 512/256: 2×5.8 ms + up to 11.6 ms of window ≈ 12–23 ms; 1024/512: ≈ 23–46 ms. The "delay" of 4.3 hops only back-dates the timestamp to the start of the attack.
- aubio has no built-in multi-band onset detector (one detection function over all bins). [SRC — no band option in onset.c/specdesc.c]

### Inferences
- [DESIGN] Recommended detector for arbitrary mixes: SuperFlux on a 24-bands/octave triangular filterbank over a 1024-point Hann STFT (hop 256 @ 48 kHz = 5.33 ms; use a 2048 or 4096 frame only for bands below ≈250 Hz), `log10(1 + λ·S)` with λ ≈ 1–10, reference = 3-band maximum filter of the frame 2 hops (≈10 ms) back, half-wave rectify, then **sum per band group** (6–8 groups, e.g. 30–80, 80–250, 250–800, 800–2500, 2500–6000, 6000–16000 Hz) to obtain one onset function per region plus one full-band sum. Causal picker per group: local max of the last 30 ms, above mean of the last 100–150 ms + δ, or ratio > 16 (essentia's two-rule form handles quiet passages), minimum inter-onset 30 ms. Start δ from the madmom/essentia values and tune by ear; expose it as a "sensitivity" control.
- Complex-domain (aubio/BTrack form) adds sensitivity to soft, pitched (legato) note changes at the price of needing phase (own FFT, not AnalyserNode). SuperFlux's max filter is the open-code answer to false onsets on vibrato; HFC is the cheapest and good only for bright percussive hits.
- Replace librosa's whole-clip normalisation with aubio-style per-bin adaptive whitening (running peak with slow decay) so that thresholds behave the same on quiet and loud material.
- With an own FFT in an AudioWorklet the achievable onset latency is ≈15–30 ms; because the listener hears the audio only after the output latency (section 4), that latency can be hidden completely for file playback.

### Gaps
- The original papers (SuperFlux DAFx-13, complex-domain onset papers, Fitzgerald DAFx-10) were not opened — paper hosts were not tried; everything above is from code.
- No measured accuracy figures (F-measure) for the causal settings were collected; madmom's docs/evaluation tables were not read.
- No open library read here ships a ready-made *per-band* causal onset detector; librosa's `channels=` is offline. The per-band grouping above is a design, not a port.

## 2. Telling short from held in real time (envelope following, decay-rate estimation, HPSS and causal variants, sinusoidal/partial tracking, tonality/flatness per band)

### Takeaway
No library read here outputs "staccato vs sustained" directly; the building blocks are (1) a per-band attack/release envelope follower plus a level-drop rule (aubio's note-off: level < level-at-onset − 10 dB; essentia's "effective duration": time above 40 % of the peak), (2) median-filter HPSS, which is causal for the percussive side and needs only ≈45–100 ms of history for the harmonic side (sevagh/Real-Time-HPSS, MIT), and (3) McAulay–Quatieri partial tracking (sms-tools/essentia constants: match if |Δf| < 20 Hz + 1 %·f), whose track "death" one hop after the last peak is the most precise note-end signal. A decision "short vs held" therefore needs ≈40–100 ms after the onset, so the painter must start a provisional mark at the onset and commit to "dab" or "stroke" when the decay evidence arrives.

### Cited Findings

#### 2.1 Envelope followers and event-shape descriptors
- [SRC] essentia Envelope: one-pole with separate coefficients `g_a = exp(−1/(sr·attack))`, `g_r = exp(−1/(sr·release))`; `env ← (1−g)·|x| + g·env`, using g_a when |x| > env, else g_r; defaults attack 10 ms, release 1500 ms. — [envelope.cpp](https://github.com/MTG/essentia/blob/23ae7ba/src/algorithms/standard/envelope.cpp)
- [SRC] essentia descriptors of one sound event (all computed on its envelope): LogAttackTime = log10(time from 20 % to 90 % of the envelope maximum) (startAttackThreshold 0.2, stopAttackThreshold 0.9); EffectiveDuration = time the envelope is above thresholdRatio 0.4 of its maximum; TCToTotal = temporal centroid / total length ("close to 0 if most of the energy lies at the beginning … impulsive sounds", 0.5 if symmetric); StrongDecay = sqrt(energy / temporal centroid). — [logattacktime.cpp](https://github.com/MTG/essentia/blob/23ae7ba/src/algorithms/sfx/logattacktime.cpp), [effectiveduration.h](https://github.com/MTG/essentia/blob/23ae7ba/src/algorithms/temporal/effectiveduration.h), [tctototal.cpp](https://github.com/MTG/essentia/blob/23ae7ba/src/algorithms/sfx/tctototal.cpp), [strongdecay.cpp](https://github.com/MTG/essentia/blob/23ae7ba/src/algorithms/sfx/strongdecay.cpp)
- [CALC] 40 % of peak amplitude = −7.96 dB; essentia's default 1500 ms release is far too slow for note-end tracking (the envelope would still be at 1/e of the peak 1.5 s after a hit).
- [SRC] aubio `notes` (monophonic note on/off): silence −70 dB, **release_drop 10 dB**, min inter-onset 30 ms, pitch median over 6 frames; note-off is sent when `curlevel < last_onset_level − release_drop_level` (level in dB of the current hop, `10·log10(mean square)`), or at silence; `last_onset_level` is stored at each detected onset. — [notes.c L27-L32, L195-L245](https://github.com/aubio/aubio/blob/ad5cf97/src/notes/notes.c#L27-L245), [mathutils.c L609-L629](https://github.com/aubio/aubio/blob/ad5cf97/src/mathutils.c#L609-L629)

#### 2.2 Harmonic/percussive separation by median filtering
- [SRC] librosa `decompose.hpss` (offline): kernel_size 31 (harmonic = median over 31 time frames per bin; percussive = median over 31 frequency bins per frame), power 2.0, margin 1.0; masks `M_h = softmask(H, margin_h·P, power)`, `M_p = softmask(P, margin_p·H, power)`, softmask = `X^p/(X^p + X_ref^p)`; margin > 1 leaves a residual that is neither. — [decompose.py (hpss)](https://github.com/librosa/librosa/blob/76f10b8/librosa/decompose.py), [utils.py (softmask)](https://github.com/librosa/librosa/blob/76f10b8/librosa/util/utils.py)
- [CALC] librosa's time median is centred: 15 frames of look-ahead = 348 ms at defaults (hop 512, 22.05 kHz). librosa has no streaming HPSS.
- [SRC] essentia has no HPSS algorithm at all (a search of `src/algorithms` for "percussive" finds only documentation strings of other algorithms). — [algorithms tree](https://github.com/MTG/essentia/tree/23ae7ba/src/algorithms)
- [SRC] sevagh/Real-Time-HPSS (MIT): "By combining the STFT and ISTFT loops and creating a sliding STFT, the separation can be done in real-time". Class constants `nwin=1024, nfft=2048, hop=512, beta=2`; `lharm = round(0.2/((nfft−hop)/fs))` frames (odd), `lperc = round(500/(fs/nfft))` bins (odd); only the last `ceil(lharm/2)` STFT columns are kept and the masks for the newest column are used: `M_h = H/(P+eps) > β`, `M_p = P/(H+eps) ≥ β` (hard masks, β = 2). README warns the Python overlap-add is buggy (analysis masks are unaffected). — [hpss_rt.py](https://github.com/sevagh/Real-Time-HPSS/blob/master/python/hpss_rt/hpss_rt.py), [README](https://github.com/sevagh/Real-Time-HPSS/blob/master/README.md)
- [CALC] at 44.1 kHz: lharm = 7 frames (4 past frames kept ≈ 46 ms of history), lperc = 23 bins (≈ 500 Hz). Extra latency beyond the STFT: 0 frames.
- [SRC] sevagh/Zen (libzen MIT): "intended to be used with a causal real-time input stream"; earlier MATLAB/Python needed "~5-10ms of processing per 10ms hop"; CUDA version "~160us for a 10ms input buffer"; hop 256 demo: 5.8 ms hop, 174 µs average processing. Demonstrates percussive-separated audio → beat tracker and harmonic-separated audio → pitch tracker. — [Zen README](https://github.com/sevagh/Zen/blob/master/README.md)

#### 2.3 Sinusoidal / partial tracking (McAulay–Quatieri peak continuation)
- [SRC] sms-tools peak detection: bin k is a peak iff `mX[k] > t` dB and greater than both neighbours; parabolic interpolation on the dB spectrum `k̂ = k + 0.5(l − r)/(l − 2v + r)`, `mag = v − 0.25(l − r)(k̂ − k)`. — [utilFunctions.py L151-L200](https://github.com/MTG/sms-tools/blob/8b685e6/smstools/models/utilFunctions.py#L151-L200)
- [SRC] sms-tools `sineTracking` (greedy): process current peaks in decreasing magnitude; each takes the nearest still-free track of the previous frame if `|f_peak − f_track| < freqDevOffset + freqDevSlope·f_peak` (defaults **20 Hz + 0.01·f**); unmatched tracks get frequency 0 (track death); leftover peaks start new tracks (birth). `sineModelAnal` defaults maxnSines 100, minSineDur 0.01 s; `cleaningSineTracks` (offline pass) deletes segments ≤ `round(fs·minSineDur/H)` frames (helper default 3). — [sineModel.py](https://github.com/MTG/sms-tools/blob/8b685e6/smstools/models/sineModel.py)
- [SRC] essentia SineModelAnal (same algorithm): maxnSines 100, maxPeaks 250, magnitudeThreshold −74 dB, freqDevOffset 20, freqDevSlope 0.01; minSineDur is commented out. — [sinemodelanal.h L61-L72](https://github.com/MTG/essentia/blob/23ae7ba/src/algorithms/synthesis/sinemodelanal.h#L61-L72)
- [SRC] essentia Vibrato (on a pitch/track-frequency contour): vibrato rate 4–8 Hz, extent 50–250 cents. — [vibrato.h](https://github.com/MTG/essentia/blob/23ae7ba/src/algorithms/tonal/vibrato.h)
- [CALC] a track's end is known one hop after its last matched peak. The default tolerance at 440 Hz is 24.4 Hz per hop ≈ 93 cents per hop, enough to follow bends and vibrato at a 5–6 ms hop.

#### 2.4 Tone versus noise
- [SRC] Spectral flatness = geometric mean / arithmetic mean of the (power) spectrum: librosa `exp(mean(ln(max(amin, S^power))))/mean(max(amin, S^power))`, amin 1e-10, power 2; Meyda `exp(mean(ln a_k))·N/Σa_k`; essentia FlatnessDB = `min(1, 10·log10(flatness)/−60)` (0 = tonal, 1 = noise; 1.0 for silence). — [librosa spectral.py L720-L838](https://github.com/librosa/librosa/blob/76f10b8/librosa/feature/spectral.py#L720-L838), [Meyda spectralFlatness.ts](https://github.com/meyda/meyda/blob/ecf2566/src/extractors/spectralFlatness.ts), [essentia flatnessdb.cpp](https://github.com/MTG/essentia/blob/23ae7ba/src/algorithms/spectral/flatnessdb.cpp)
- [SRC] librosa spectral contrast (peak-to-valley per octave band, a per-band tonality measure): 6 bands from fmin 200 Hz, quantile 0.02. — [spectral.py L357-L560](https://github.com/librosa/librosa/blob/76f10b8/librosa/feature/spectral.py#L357-L560)
- [SRC] Meyda spectral crest = max/rms of the magnitude spectrum (high = one dominant partial). — [spectralCrest.ts](https://github.com/meyda/meyda/blob/ecf2566/src/extractors/spectralCrest.ts)

### Inferences
- **Why the painting draws long strokes for staccato sounds** (most likely): any smoothing with a long release (AnalyserNode `smoothingTimeConstant` 0.8 ≈ 75 ms time constant at 60 fps plus an 8192-sample window ≈ 170–186 ms, see section 3) stretches a 30 ms hit into a 200+ ms plateau, and nothing in the pipeline signals "the sound has ended". The fix is an explicit per-event state machine driven by an unsmoothed short-window envelope.
- [DESIGN] Per-band event state machine (hop ≈ 5.3 ms, bands as in section 1):
  1. **ONSET** (from the band's SuperFlux peak): open a *provisional* event; record `L0` = maximum band level (dB) in the first 15–20 ms; give the painter an immediate small mark (the "tap"), not a stroke.
  2. **WATCH** for up to ≈100 ms: track `D(t) = L0 − L(t)` with a fast follower (attack ≈ 0–2 ms, release ≈ 20–30 ms, i.e. essentia's follower with a ≈50× shorter release).
     - `D ≥ 6–10 dB` within ≈60 ms (aubio uses 10 dB for note-off; essentia's 40 % ≈ 8 dB) → **SHORT** (dab/splat sized by L0, shaped by flatness: noise → spatter, tone → dot). Typical decision time 30–60 ms.
     - `D < 3 dB` after ≈80–100 ms **and** tonal evidence (band flatness low, or a partial track alive ≥ 8–12 hops, or H/(H+P) rising) → **HELD**: start extending a stroke from the tap.
     - Otherwise classify by decay slope (least-squares dB/s over the watch window; T60 = 60/|slope|): T60 < ≈0.4 s short, > ≈1 s held, in between = "plucked/decaying" (a stroke that tapers with the envelope).
  3. **HELD** ends (note-off) on the first of: the band's partial tracks die (unmatched for 2 hops); level < L0 − 10…20 dB; level below the band's noise floor (slow minimum tracker); a new onset in the same band (legato re-articulation → end the stroke and start the next, joined).
  The numeric thresholds are proposals to be tuned by ear; only the 10 dB drop, the 40 % rule, the 20 Hz + 1 % tolerance and the median lengths come from code.
- Causal HPSS as an *instant* percussive cue: the frequency-direction median needs no history, so `P/(H+P)` for the newest frame is available at the onset frame itself — a broadband click scores high immediately. The harmonic median only "believes" a tone after it has persisted about half the kernel (≈ 45 ms with Real-Time-HPSS constants, ≈ 100 ms with a 200 ms kernel), which is the same wait as the WATCH stage; the two cues can be fused.
- Partial tracking is the only one of these that separates *simultaneous* held notes in the same band and follows glides/vibrato (stroke direction/curvature can follow the track frequency derivative; 4–8 Hz, 50–250 cents oscillation = vibrato → wavy stroke).
- Because a firm short/held decision needs 40–100 ms and the audio is heard `outputLatency` later (plus an optional DelayNode for file playback, section 4), the decision can usually be made *before the listener hears the note end*; for file playback with a 100 ms audio delay the painter can know the articulation at the moment the note becomes audible.

### Gaps
- "How many milliseconds are needed to decide percussive vs sustained" has no single sourced number; the 40–100 ms figure is derived from the median lengths, the hop sizes and the level-drop rules above, not from a published evaluation.
- loris (reassigned bandwidth-enhanced partial tracking) was not read (not located on GitHub in this session); its licence was not verified.
- No open *JavaScript/TypeScript* real-time HPSS or partial tracker was found or read; the items above are Python/C++ and would be ports (MIT ones) or re-implementations from formulas (AGPL ones).
- Fitzgerald's and Driedger's papers (kernel-length recommendations, e.g. the often-quoted ≈200 ms / ≈500 Hz) were not opened; the 0.2 s and 500 Hz figures here are from the Real-Time-HPSS code.

## 3. Getting a log-frequency (constant-Q-like) spectrum with good time resolution in the browser (AnalyserNode limits vs AudioWorklet with own FFTs, multi-resolution STFT, sliding DFT, filter banks; what open projects do; sizes, hop, CPU)

### Takeaway
`AnalyserNode` cannot do this job: it is pull-based (one FFT per main-thread call, at most one per render quantum), has a fixed Blackman window, no phase, no hop control and built-in temporal smoothing; the open visualisers built on it (audioMotion-analyzer: fftSize 8192, smoothing 0.5) trade ≈170–190 ms of time smear for bass resolution. The workable design is an `AudioWorkletProcessor` (128-frame quanta = 2.67 ms at 48 kHz) feeding its own analysis: either a multi-resolution STFT (e.g. 4096 for bass, 1024 for mids, 256 for treble, hop 128–512) mapped to 24 bands/octave, or FFmpeg-showcqt's "one FFT + sparse per-bin kernel", or a constant-Q sliding DFT (jurihock/qdft, MIT) whose per-bin window is ≈28 ms at 1 kHz but still ≥100 ms below 100 Hz — the bass time/frequency trade-off is physical, not an implementation limit.

### Cited Findings

#### 3.1 AnalyserNode limits (Web Audio spec) — [SRC] [index.bs @42e974a](https://github.com/WebAudio/web-audio-api/blob/42e974a/index.bs)
- fftSize "MUST be a power of two in the range 32 to 32768", default 2048; "The most recent fftSize frames are used in computing the frequency data"; defaults smoothingTimeConstant 0.8, minDecibels −100, maxDecibels −30. (≈ L5010-L5062)
- Algorithm: down-mix to mono → Blackman window (α = 0.16: `w[n] = 0.42 − 0.5cos(2πn/N) + 0.08cos(4πn/N)`) → FFT scaled 1/N → smoothing `X̂[k] = τ·X̂₋₁[k] + (1−τ)·|X[k]|` → `20·log10`. (≈ L5218-L5330)
- "If another call to getFloatFrequencyData() or getByteFrequencyData() occurs within the same render quantum as a previous call, the current frequency data is not updated with the same data. Instead, the previously computed data is returned." (≈ L5149)
- [CALC] Consequences: (i) the "hop" is the interval between main-thread calls (≈16.7 ms at 60 fps, jittery; longer when the tab is busy); (ii) τ is applied per call — at 60 calls/s τ = 0.8 is a 75 ms time constant, τ = 0.5 is 24 ms; τ must be 0 for onset work; (iii) magnitude only — no complex-domain detection, no phase-based frequency refinement; (iv) window length = latency/smear: 2048 → 43 ms, 8192 → 171 ms, 32768 → 683 ms at 48 kHz, with the window centre half of that in the past; (v) mono down-mix (one analyser per channel needed for stereo); (vi) samples between calls can be skipped if fftSize < samples per display frame (800 at 48 kHz/60 fps).
- Render quantum: "default value is 128, and it can be configured by setting renderSizeHint" (integer | "default" | "hardware"; "a hint that might not be honored"); `renderQuantumSize` attribute reports the actual value. (≈ L783-L815, L2396-L2410, L12228-L12236). [CALC] 128 frames = 2.67 ms @48 kHz, 2.90 ms @44.1 kHz.
- `AudioWorkletGlobalScope.currentFrame` = "the current frame of the block of audio being processed"; `currentTime` = "the context time of the block of audio being processed". (≈ L10727-L10740) → every analysis frame can be stamped with an exact context time.

#### 3.2 What open projects do — [SRC] unless marked
- **audioMotion-analyzer** (AGPL): two native AnalyserNodes (one per channel), `getFloatFrequencyData` once per animation frame; defaults fftSize 8192, smoothing 0.5, −85…−25 dB, 20 Hz–22 kHz. Optional A/B/C/D/ITU-468 weighting applied in dB per bin. No worklet, no own FFT, no multi-resolution. — [audioMotion-analyzer.js L92-L130, L286, L1336-L1470, L1900-L1930, L2157-L2182](https://github.com/hvianna/audioMotion-analyzer/blob/bd226d1/src/audioMotion-analyzer.js)
- **Meyda** (MIT): own FFT on buffers delivered by the deprecated `ScriptProcessorNode` on the main thread (`createScriptProcessor`, `onaudioprocess`), default bufferSize 512 (256 in the Web Audio wrapper), hop = bufferSize unless set; linear-frequency features plus 26 mel bands, 24 Bark bands, 12 chroma. — [meyda-wa.ts L104-L190](https://github.com/meyda/meyda/blob/ecf2566/src/meyda-wa.ts#L104-L190), [main.ts L240-L249](https://github.com/meyda/meyda/blob/ecf2566/src/main.ts#L240-L249)

[CALC] tlength: 0.169 s @20 Hz, 0.163 s @100 Hz, 0.118 s @1 kHz, 0.061 s @4 kHz, 0.031 s @10 kHz; hop = 1/150 s = 6.7 ms.
- **jurihock/qdft** (MIT; C++, Rust, Python — no JS): constant-Q *sliding* DFT, recursive, one update per sample, "an efficient implementation without the FFT"; default 24 bins/octave (quarter tone), Hann window; "optional quality control parameter to smoothly reduce low frequency bandwidth and improve the time resolution"; "optional analysis latency control parameter". With the ERB-like quality option (beta = 6.70): 122 ms @50 Hz, 104 ms @100 Hz, 51 ms @440 Hz, 28 ms @1 kHz, 8.1 ms @4 kHz. Bins for 50 Hz–22.05 kHz: 211. - **jurihock/sdft** (MIT): linear sliding DFT ("modulated SDFT … guaranteed to be stable"), windows boxcar/Hann/Hamming/Blackman, "real-time low latency (compared to STFT latency)". — [README](https://github.com/jurihock/sdft/blob/main/README.md)
- **essentia** (AGPL) ships `constantq`, `nsgconstantq`, `nsgconstantqstreaming`, `spectrumCQ`, `erbbands`, `gfcc`, `triangularbands`, `logspectrum` algorithms (file names read; internals not read). — [standard/](https://github.com/MTG/essentia/tree/23ae7ba/src/algorithms/standard), [spectral/](https://github.com/MTG/essentia/tree/23ae7ba/src/algorithms/spectral)
- **essentia.js** is AGPL-3.0 (README badge). — [README](https://github.com/MTG/essentia.js/blob/master/README.md). [SEC] it is a WebAssembly build of essentia with AudioWorklet examples; not verified in this session.

### Inferences
- [DESIGN] Recommended architecture: `source → AudioWorkletNode("tap")` (and in parallel `source → [DelayNode] → destination`). The worklet's `process()` only copies each 128-frame block into a ring buffer (a `SharedArrayBuffer` shared with a dedicated Worker when cross-origin isolation is available, otherwise batched `postMessage` with transferable buffers) together with `currentFrame`; all FFT/feature work runs in the Worker so the audio thread never stalls; results (timestamped in context time) go to the render loop.
- [DESIGN] Three-resolution STFT at 48 kHz: **bass** FFT 4096 / hop 512 for < 250 Hz (pitch-resolving, 43 ms centre delay), **mid** FFT 1024 / hop 256 for 250 Hz–4 kHz (11 ms), **treble** FFT 256 / hop 128 for > 4 kHz (2.7 ms); each mapped by triangular filters to a common 24-bands/octave grid (≈ 9 octaves × 24 = 216 bands) at the fastest hop (hold the slower layers). Onsets come from the mid/treble layers (fast); the bass layer supplies pitch and sustain. For bass *onsets* add a time-domain path: band-pass (2 biquads) → rectifier → fast envelope, which has no window delay.
- A true CQT (showcqt-style kernel on one 8192 FFT, or qdft) gives a nicer picture but its low bins are ≥100 ms wide; use it for the *display/pitch* layer, not for onset timing. qdft's per-sample recursion is attractive for a worklet (no block latency) but costs roughly 4× the multi-resolution STFT and exists only in C++/Rust/Python (port or compile to WASM; MIT).
- Phase-based frequency refinement (instantaneous frequency from phase advance) or parabolic interpolation (sms-tools formula, section 2.3) recovers sub-bin pitch from the short windows, so the 1024 layer can still label notes to the semitone above ≈ 200 Hz for isolated partials.

### Gaps
- No gammatone, Goertzel-bank or biquad-bank implementation was read in this session; their cost/latency statements here are limited to the general remark that an IIR band-pass + envelope has no block delay. [SEC]
- showcqt-js (JS/WASM port of showcqt) could not be fetched (README path returned 404); its licence and API are unverified.
- CPU cost in a real browser (JS vs WASM, per device) was not measured; only operation counts are given. essentia.js real-time performance figures were not read.
- Browser support status (Chromium/WebView2/WebKit versions) for `renderSizeHint` / `renderQuantumSize` was not checked; the spec text says the hint may be ignored.

## 4. Time alignment (delay between analysis and what the listener hears; outputLatency, baseLatency; keeping visuals in sync)

### Takeaway
An analysis node sees samples *before* they are audible: the gap is `baseLatency + outputLatency` (spec definitions), and `getOutputTimestamp()` gives the exact mapping from the audio clock to `performance.now()`. Stamp every analysis event with context time, subtract the known analysis delay, and schedule the paint for the moment `getOutputTimestamp().contextTime` reaches that time; for file playback, a `DelayNode` on the audible path (analysis tapped before it) buys any look-ahead the analysis needs.

### Cited Findings
- [SRC] `baseLatency`: "number of seconds of processing latency incurred by the AudioContext passing the audio from the AudioDestinationNode to the audio subsystem. It does not include any additional latency that might be caused by any other processing between the output of the AudioDestinationNode and the audio hardware and specifically does not include any latency incurred [by] the audio graph itself"; example "(2·128)/44100 = 5.805 ms". — [index.bs ≈ L1742-L1757](https://github.com/WebAudio/web-audio-api/blob/42e974a/index.bs)
- [SRC] `outputLatency`: "The estimation in seconds of audio output latency, i.e., the interval between the time the UA requests the host system to play a buffer and the time at which the first sample in the buffer is actually processed by the audio output device … An outputLatency attribute value depends on the platform and the connected audio output device hardware. The outputLatency attribute value may change while the context is running or the associated audio output device changes. It is useful to query this value frequently when accurate synchronization is required." — [index.bs ≈ L1759-L1774](https://github.com/WebAudio/web-audio-api/blob/42e974a/index.bs)
- [SRC] `getOutputTimestamp()` returns `contextTime` = "the time of the sample frame which is currently being rendered by the audio output device (i.e., output audio stream position), in the same units and origin as context's currentTime" and `performanceTime` = "the moment when the sample frame corresponding to the stored contextTime value was rendered by the audio output device, in the same units and origin as performance.now()". — [index.bs ≈ L1946-L1968](https://github.com/WebAudio/web-audio-api/blob/42e974a/index.bs)
- [SRC] The current draft also defines `AudioContext.playbackStats` (`AudioPlaybackStats`: underrunDuration, underrunEvents, totalDuration, averageLatency, minimumLatency, maximumLatency, resetLatency()). — [index.bs ≈ L1803, L11862-L11871](https://github.com/WebAudio/web-audio-api/blob/42e974a/index.bs)
- [SRC] `latencyHint` default "interactive". — [index.bs ≈ L2361](https://github.com/WebAudio/web-audio-api/blob/42e974a/index.bs)
- [SRC] In the worklet, `currentTime`/`currentFrame` identify the block being processed. — [index.bs ≈ L10727-L10740](https://github.com/WebAudio/web-audio-api/blob/42e974a/index.bs)
- [SRC] audioMotion-analyzer contains no use of `outputLatency`, `baseLatency` or `getOutputTimestamp` (searched the source) — it simply draws the analyser's current data each frame. — [audioMotion-analyzer.js](https://github.com/hvianna/audioMotion-analyzer/blob/bd226d1/src/audioMotion-analyzer.js)
- [SRC] aubio back-dates detected onsets by a fixed "delay" (4.3 hops; 4.6 for complex) so reported times match the attack start; aubio tempo exposes `set_delay` for the same purpose. — [onset.c L283-L302](https://github.com/aubio/aubio/blob/ad5cf97/src/onset/onset.c#L283-L302), [tempo.c L120-L143](https://github.com/aubio/aubio/blob/ad5cf97/src/tempo/tempo.c#L120-L143)

### Inferences
- [DESIGN] Timeline bookkeeping: `t_event = blockContextTime + sampleOffset/sr − analysisDelay` (analysisDelay = half window + picker look-ahead, e.g. ≈ 11 + 5 ms). An event at context time `t_event` is *heard* when the output position reaches it: each animation frame read `ts = ctx.getOutputTimestamp()`, compute `audibleNow = ts.contextTime + (performance.now() − ts.performanceTime)/1000`, and release every queued event with `t_event ≤ audibleNow + displayLead` (displayLead ≈ one display frame, ≈ 8–16 ms, to cover compositor delay). Fallback where `getOutputTimestamp` is missing/zero: `audibleNow ≈ ctx.currentTime − ctx.outputLatency` (re-read `outputLatency` regularly; it changes with the output device).
- The analysis therefore has a free look-ahead budget of roughly `baseLatency + outputLatency`. [SEC] Typical desktop values are on the order of 10–50 ms for wired outputs and 150–300 ms for Bluetooth; not measured here.
- For file playback, insert `DelayNode(delayTime = L)` only on the path to the destination and tap the analysis before it: the analysis then runs `L` ahead of the ears (L = 50–100 ms covers the short/held decision of section 2 and a look-ahead peak picker). For live input this is not acceptable (the performer would hear the delay), so live mode must use the provisional-mark strategy.
- Because the whole file is available after `decodeAudioData`, the most accurate option is to pre-analyse it off-line in a Worker (non-causal: centred medians, look-ahead peak picking, off-line beat tracking, whole-file key) and merely *play back* the event list against the audio clock; the real-time path is then needed only for live input and for the app's own synthesised output.

### Gaps
- No open project was found in this session that documents an end-to-end visual-sync method using `getOutputTimestamp()`; the scheme above is derived from the spec.
- Actual `outputLatency` accuracy on Windows/WebView2 (especially with Bluetooth or exclusive-mode drivers) and support status in WebKit-based webviews were not verified.
- Display pipeline latency (compositor, monitor) is not exposed by any API read here; the `displayLead` constant must be calibrated by eye/ear (e.g. a click-and-flash calibration screen).

## 5. Loudness and dynamics (BS.1770 K-weighting, momentary 400 ms / short-term 3 s, crest factor, dynamic range; A-weighting vs the natural tilt of music for display)

### Takeaway
Use the two-biquad K-weighting filter from libebur128 (MIT; coefficients computed for any sample rate) with `L = −0.691 + 10·log10(mean square)` over 400 ms (momentary) and 3 s (short-term) for mood-level loudness, a much faster (≈ 50–100 ms) K-weighted RMS for gesture size, and loudness range (10th–95th percentile of gated short-term values) plus crest factor for "dynamics". For *display/per-band comparison*, A-weighting is the wrong tool (−19 dB at 100 Hz, −30 dB at 50 Hz); a fixed tilt of about +3 to +4.5 dB/octave or, better, aubio-style per-bin adaptive whitening, puts bass and treble on a comparable footing.

### Cited Findings

### Inferences
- [DESIGN] Three loudness time scales: (a) **gesture** — K-weighted RMS with ≈ 50–100 ms integration, per band and full band, drives stroke width/pressure instantly; (b) **momentary** 400 ms — drives overall intensity/energy; (c) **short-term** 3 s and a slow (10–30 s) running mean — used only to *normalise* (a) and (b), so a quiet song and a loud song both use the full visual range, and to compute "dynamics" = spread between the 95th and 10th percentile of recent short-term values (LRA-style) and crest = peak − RMS over ≈ 3 s.
- For band-to-band comparisons use whitening (each band relative to its own recent peak/mean), not A-weighting: A-weighting models low-level hearing sensitivity and would make kick and bass nearly invisible; a +3 to +4.5 dB/octave tilt is a reasonable static display default, whitening is the adaptive version.

- ITU-R BS.1770 and EBU R128/Tech 3341–3342 documents were not opened; constants are from libebur128/essentia code.
- The −4.5 dB/octave figure for the natural tilt of music is not backed by any source read here.
- No open-code crest-factor/PLR implementation was read.

## 6. Features for mood, vibe and texture (formulas in open code; real-time tempo/beat; chroma, key, mode, harmonic change; which combinations predict energy/arousal and valence)

### Takeaway
Energy/arousal is well predicted by a handful of cheap features — loudness (RMS), strength of the 1–10 Hz rhythmic fluctuation (beat salience/onset rate), spectral centroid (brightness) and spectral entropy/flatness (noisiness), all with positive sign — while valence depends mostly on tonal features (key clarity and majorness positive; roughness, harmonic-change rate and loudness variability negative) and is intrinsically less reliable; the only open code read that gives actual regression weights is MIRtoolbox's `miremotion` (GPL-2.0-only: use the published model, not the code). For beat/tempo in real time, BTrack (GPL-3.0-or-later; predicts beats half a beat ahead, 80–160 BPM) and aubio tempo (GPL-3.0-or-later; ≈ 6 s lock-in, 1.5 s update) are the causal open algorithms; librosa's beat tracker is offline and madmom's neural trackers need non-commercial model files.

### Cited Findings

#### 6.1 Spectral/texture features (formulas)

#### 6.4 Which feature combinations predict energy/arousal and valence
- [SRC] MIRtoolbox `miremotion` — "Selection of features and coefficients are taken from … (2009) Prediction of multidimensional emotional ratings in music from audio using multivariate regression models, ISMIR 2009, pp. 621-626 … multiple linear regression with 5 best predictors"; the file warns the model "is not correctly calibrated with this version of MIRtoolbox (but with version 1.3 only)". z(x; μ, σ) = (x − μ)/σ. — [miremotion.m L18-L32, L133-L172, L377-L465](https://github.com/olivierlar/mirtoolbox/blob/71d6265/MIRToolbox/%40miremotion/miremotion.m)
  - **Activity (energy/arousal)** = 5.4861 + **0.6664**·z(mean RMS; 0.0559, 0.0337) + **0.6099**·z(peak of the fluctuation spectrum, i.e. strength of the dominant rhythmic periodicity; 13270.18, 10790.66) + **0.4486**·z(mean spectral centroid; 1677.7 Hz, 570.34) − **0.4639**·z(mean spectral spread) + **0.7056**·z(spectral entropy; 0.954, 0.0258).
  - **Valence** = 5.2749 − **0.3161**·z(std of RMS; 0.024254, 0.015667) + **0.6099**·z(fluctuation peak) + **0.8802**·z(key clarity; 0.5123, 0.092) + **0.4565**·z(mode/majorness; −0.002, 0.0487) + **0.4015**·z(spectral novelty; 131.95, 47.65).
  - **Tension** = 5.4679 + **0.5382**·z(std RMS) − **0.5406**·z(fluctuation peak) − **0.6808**·z(key clarity) + **0.8629**·z(harmonic change, HCDF; 0.2962, 0.0459) − **0.5958**·z(chroma novelty; 71.84, 46.92).
  - Discrete emotions: Happy ↑ fluctuation peak (+0.74), ↓ spectral spread (−0.40), ↑ chroma-peak variability (+0.40), ↑ key clarity (+0.78), ↑ majorness (+0.62). Sad ↑ spread (+0.43), ↓ chroma-peak variability (−0.31), ↓ majorness (−0.52), ↓ HCDF (−0.60), ↑ tonal novelty (+0.45). Tender ↓ centroid (−0.27), ↓ variability of `rg` (−0.49; `rg` is the roughness-derived variable in that file — its definition line was not displayed in my read), ↑ key clarity (+0.52), ↓ HCDF (−0.40), ↑ spectral novelty (+0.34). Anger ↑ mean `rg` (roughness, +0.55), ↓ key clarity (−0.58), ↑ spectral entropy (+0.28), ↓ chroma novelty (−0.30). Fear ↑ RMS variability (+0.41), ↓ attack time (−0.64), ↓ fluctuation peak (−0.25), ↓ key clarity (−0.99), ↓ majorness (−0.31).
  - Feature frames used there: RMS and spectrum 46 ms frames / 50 % hop; onsets from a 15-band filterbank; pulse clarity 2 s frames; spectral entropy 1.5 s frames; spectral novelty 100 ms frames up to 5 kHz; chroma novelty 200 ms frames.
- [SEC] Broader music-emotion-recognition literature (reviews and regression studies; not re-read): arousal rises with loudness, tempo/onset rate, brightness (centroid, high-frequency energy), spectral flux and roughness, and with sharp attacks/staccato articulation; valence rises with major mode, consonance/key clarity and (in fast, major contexts) tempo, and falls with roughness/dissonance and minor mode; staccato articulation is associated with energetic/playful/agitated expression and legato with tender/sad/solemn expression; audio models predict arousal consistently better than valence.

### Inferences
- [DESIGN] Real-time mood vector, each term z-scored against a slow running mean/variance (30–60 s) because the absolute MIRtoolbox normalisation constants are tied to one toolbox version: **energy** = +loudness (momentary) + onset rate (events/s over 4 s) + beat salience (peak of the onset-envelope autocorrelation or BTrack's cumulative score) + centroid + flatness/entropy; **valence** = +key clarity (best key correlation over a 5–10 s exponentially-weighted chroma) + majorness (best major corr − best minor corr) − roughness − loudness variability; **tension** = +harmonic change rate (tonal-centroid distance) − key clarity + roughness. Smooth with 2–5 s time constants so the palette drifts rather than flickers; show uncertainty (e.g. desaturate) when key clarity is low.
- Articulation itself (ratio of SHORT to HELD events from section 2, mean attack time) is a mood/texture feature and comes for free from the event classifier.
- Key detection needs several seconds of chroma; treat it as slow state, never as an instant reaction. Mode (major/minor) flips are unreliable on short windows — use hysteresis.
- Beat tracking: run BTrack's algorithm on the percussive-weighted onset function (Zen's demo does exactly that) for beat-synchronous effects; fall back to raw onsets when its confidence (cumulative-score contrast) is low or the music has no steady pulse.

### Gaps
- The music-emotion literature itself (the 2009 regression paper's reported accuracy, later reviews, dataset benchmarks) was not opened; only the model as coded in MIRtoolbox was read, and its authors flag it as uncalibrated for current toolbox versions.
- MIRtoolbox's `mirfluctuation`, `mirkeystrength`, `mirmode`, `mirhcdf`, `mirnovelty` internals were not read (only their use in `miremotion`).
- No causal, permissively-licensed neural emotion or tempo model was looked for; essentia's TensorFlow models were not examined (and essentia is AGPL).

## 7. Decoding and playing a user's audio file in the browser for analysis (decodeAudioData vs MediaElementAudioSourceNode; formats in Chromium/WebView2), and analysing the app's own master output

### Takeaway
`decodeAudioData` gives the whole file as PCM in memory (resampled to the context rate), which enables off-line pre-analysis in a Worker and sample-accurate scheduling; `MediaElementAudioSourceNode` streams with low memory but only allows causal analysis and outputs silence for cross-origin media without CORS. Chromium's default audio decoders cover FLAC, MP3, Opus, Vorbis and PCM variants in every build, and AAC only in builds with proprietary codecs. The app's own master output is analysed by connecting the master bus to the same analysis worklet — no loopback device is involved.

### Cited Findings
- [SRC] `decodeAudioData(audioData, …)`: "Asynchronously decodes the audio file data contained in the ArrayBuffer … Audio file data can be in any of the formats supported by the <audio> element. The buffer passed to decodeAudioData() has its content-type determined by sniffing"; the decoded audio is resampled to the context's sample rate. — [index.bs ≈ L1208-L1232, L1313](https://github.com/WebAudio/web-audio-api/blob/42e974a/index.bs)
- [SRC] Media element path: the element's audio "must be resampled to match the context's sample rate"; "a MediaElementAudioSourceNode MUST output silence instead of the normal output of the HTMLMediaElement if it has been created using an HTMLMediaElement for which the execution of the fetch algorithm labeled the resource as CORS-cross-origin". — [index.bs ≈ L8688, L8770-L8786](https://github.com/WebAudio/web-audio-api/blob/42e974a/index.bs)
- [SRC] Chromium `IsDefaultDecoderSupportedAudioType`: returns true for FLAC, MP3, Opus, PCM, PCM µ-law, PCM S16BE, PCM S24BE, PCM A-law, Vorbis; AAC → supported except the xHE-AAC profile, which needs a platform decoder (Android/Mac/Windows builds with the mojo audio decoder); returns false for AMR-NB/WB, GSM-MS, ALAC, MPEG-H; AC-3/E-AC-3, AC-4, DTS and IAMF depend on build flags/platform. - [SRC] The local project contains a `src-tauri` directory (listing of `/home/user/M-Theory-App`), i.e. the page runs inside a system webview.
- [SEC] On Windows that webview is WebView2 (the Chromium engine of the system browser, a branded build with proprietary codecs, so AAC/M4A normally decodes); on macOS and Linux Tauri uses WebKit-based webviews whose codec set, AudioWorklet behaviour and `outputLatency` support differ from Chromium. Not verified in this session.
- [SEC] Container support (WAV, OGG, WebM, MP4/M4A, MP3, FLAC files) follows the codecs above; the container/demuxer list was not read from source.

### Inferences
- [DESIGN] File mode: read the file as an ArrayBuffer → `decodeAudioData` → (1) hand a copy of the channel data to a Worker for off-line analysis (all of sections 1, 2 and 6 with non-causal settings: centred HPSS medians, look-ahead peak picking, whole-file key/tempo; this runs many times faster than real time) and (2) play with `AudioBufferSourceNode.start(when, offset)`; visual events are scheduled against `getOutputTimestamp()` (section 4). Seeking = restart the source with a new offset. Start painting immediately with the real-time analyser and switch to the pre-computed event list as soon as the Worker has passed the play-head.
- Long files / low memory: use `<audio>` + `createMediaElementSource` with the real-time worklet analysis and a `DelayNode` for look-ahead; fetch local files via blob/object URLs or the app's own protocol so they are same-origin (otherwise the node is silent).
- Own master output: `masterGain.connect(analysisWorklet)` in parallel with `masterGain.connect(ctx.destination)`; the worklet needs no audible output. Because the app also knows its own note-on/note-off events, use those as ground truth for app-generated notes and reserve the audio analysis for imported/live audio and for the mixed result (loudness, spectrum, mood).
- Decode failures should fall back gracefully (format not supported by the platform webview), and the supported-format list shown to the user should be probed at run time (`canPlayType` / trial decode) rather than hard-coded, since it differs between WebView2 and WebKit webviews.

### Gaps
- WebView2-specific codec behaviour, and Tauri's webview differences on macOS/Linux, were not verified from source or documentation in this session.
- Whether an `AudioWorkletNode` with zero outputs keeps being processed in all engines when only its input is connected was not checked in the spec text.
- `decodeAudioData` performance (time to decode long files) and maximum buffer size limits in Chromium were not measured or read.
- Capturing audio from *other* applications or the system output (as opposed to a file or the app's own graph) was out of scope and not researched.
