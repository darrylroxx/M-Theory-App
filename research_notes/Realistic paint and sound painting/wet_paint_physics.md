## 1. David Li's "Fluid Paint" (github.com/dli/paint): complete algorithm, shader structure, grid sizes, licence

### Takeaway
Fluid Paint is NOT a 3D grid fluid: it is a 2D Stam-style "stable fluids" solver (only 2 Jacobi iterations, no vorticity, no viscosity term) run in a scissored dirty rectangle around recent brush splats for 60 frames, plus a 3D position-based-dynamics bristle brush (100 bristles x 10 vertices) that splats colour and velocity as thousands of small capsule quads. Paint "height" is simply the accumulated alpha channel of the RGBA float paint texture; a Sobel filter on it gives a normal, lit with a GGX specular + weak diffuse term. Licence MIT (GPL-3.0-or-later compatible).

- [SRC] 2) Pressure cleared to 0 every frame, then 2 Jacobi iterations: `p' = (pL + pR + pB + pT - div) / 4`. — [jacobi.frag](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/shaders/jacobi.frag)
- [SRC] 3) Projection: `v' = v - vec2(pR - pL, pT - pB) / 2`. — [subtract.frag](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/shaders/subtract.frag)
- [SRC] 4) Advect paint with dissipation 1.0 (paint is conserved, never fades), then 5) advect velocity with dissipation = `fluidity` (0.8 per frame, i.e. velocity dies very fast: this is what makes it feel like viscous paint, not water). Advection is semi-Lagrangian RK2 (midpoint): `vel = tex(v, x).rg * 100; xh = x - vel*0.5*dt; vh = tex(v, clamp(xh)).rg * 100; out = tex(input, clamp(x - vh*dt)) * dissipation`, in texel units, clamped to the dirty rectangle (`u_min`,`u_max`). — [advect.frag](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/shaders/advect.frag), [simulator.js L469-L475](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/simulator.js#L469-L475)
- [SRC] There is no vorticity confinement, no diffusion/viscosity solve, no gravity and no drying variable. Paint "stops" because (a) velocity is multiplied by 0.8 each frame, and (b) each splat's bounding rectangle is only simulated for 60 frames after the splat, after which the rectangle is dropped and simulation stops (the code also attempts to clear the velocity textures at that point, but see the argument bug noted in section 9). — [simulator.js L479-L492](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/simulator.js#L479-L492)
- [SRC] Dirty-rectangle optimisation: every pass uses `viewport` + `SCISSOR_TEST` set to the union of live splat rectangles (brush position +/- `ceil(scale*4.5) + ceil(filteredSpeed*1.1)`, where filteredSpeed is the max of the last 15 frame speeds). If no splat areas are live, `simulate()` returns false and nothing is drawn (`needsRedraw` stays false). — [simulator.js L226-L262](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/simulator.js#L226-L262), [brush.js L4, L249-L251](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/brush.js#L4)

**Paint transfer ("splatting")** — [splat.vert](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/shaders/splat.vert), [splat.frag](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/shaders/splat.frag), [simulator.js L245-L343](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/simulator.js#L245-L343)
- [SRC] Geometry: for each bristle, each of 9 segments, 8 sample points along the segment; each sample is a quad whose vertex shader reads that point's current and previous 3D position from the position textures and stretches the quad into a capsule covering the swept line from previous to current xy (half-width `u_splatRadius`). Points with `z > zThreshold` (not touching the canvas) are thrown off-screen. The fragment computes distance to the swept segment and a linear falloff `m = max(1 - d/radius, 0)`.
- [SRC] Colour splat: output `vec4(color.rgb, color.a * m)`, blended `blendFuncSeparate(SRC_ALPHA, ONE_MINUS_SRC_ALPHA, ONE, ONE)` — i.e. RGB is alpha-lerped toward brush colour ("pickup"/mixing in place is just this lerp + advection), while the alpha (height) channel is purely additive and unbounded (float texture). `SPLAT_RADIUS = 0.05 * brushScale`. Splat alpha = lerp(minAlpha, maxAlpha, userAlpha) with thin brush (10 bristles) 0.002..0.08 and thick brush (100 bristles) 0.002..0.025. — [paint.js L61-L70, L592-L614](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/paint.js#L61-L70)
- [SRC] Velocity splat: same quads, output `vec4(clampVelocity(v * u_velocityScale), 0, m)` where v is the bristle-point velocity interpolated previous->current along the quad, `MAX_SPEED = 2.0`, blended additively `(ONE, ONE)` into the velocity texture. `velocityScale = SPLAT_VELOCITY_SCALE(0.14) * splatAlpha * resolutionScale`. (Velocity texture units are later multiplied by 100 in advect.frag to get texels/second.)
- [CALC] Splat geometry size: 100 bristles x 9 segments x 8 samples = 7,200 quads = 28,800 vertices / 43,200 indices, drawn twice per frame (colour, velocity) while painting.

**Colour model**
- [SRC] The brush HSV colour is converted with the ordinary HSV->RGB formula but the result is *interpreted* as RYB and stored; at display time `rybToRgb()` trilinearly interpolates an 8-corner RYB cube: (0,0,0)->white (1,1,1); R->(1,0,0); Y->(1,1,0); B->(0.163,0.373,0.6); RY->(1,0.5,0); YB->(0,0.66,0.2); RB->(0.5,0,0.5); RYB->(0.2,0.094,0). So mixing happens linearly in RYB (subtractive-like: yellow + blue = green), and the cube lookup is ~8 multiply-adds per pixel. Optional "RGB" mode is `1 - ryb.yxz`. — [painting.frag L23-L48](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/shaders/painting.frag#L23-L48), [paint.js L153-L175](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/paint.js#L153-L175)

**Lighting from paint height** — [painting.frag](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/shaders/painting.frag)
- [SRC] Height = alpha channel. Gradient = 3x3 Sobel on height; `normal = normalize(vec3(gx, gy, u_normalScale))` with `NORMAL_SCALE = 7.0 / resolutionScale`. Light direction `normalize(0,1,1)`, eye `(0,0,1)`. Diffuse `= saturate(dot(L,N)) * 0.15 + 0.85` (`DIFFUSE_SCALE = 0.15`). Specular = Cook-Torrance: `D = a2 / (PI * ((N.H)^2 (a2-1) + 1)^2)` with `a = ROUGHNESS = 0.075`; Smith-style `G = 1/((N.L + sqrt(a2 + (1-a2)(N.L)^2)) (N.V + sqrt(a2 + (1-a2)(N.V)^2)))`; Schlick Fresnel `F = (1-F0)(1-L.H)^5 + F0`, `F0 = 0.05`. Final `rgb = rybToRgb(c) * diffuse + D*G*F * SPECULAR_SCALE(0.5)`. — [paint.js L93-L98, L652-L657](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/paint.js#L93-L98)
- [SRC] Bristle furrows are not modelled separately: they appear because each bristle deposits its own thin additive ridge of alpha (radius 0.05 x scale) and the Sobel normal picks the ridges up.

**Per-frame cost**
- [CALC] While painting: brush solver = 1 predict + 1 pin + 20 x (1 pin + 2 distance + 3 bending + 1 plane) + 1 velocity = 143 draw calls, but each on a 100x10 texel target (negligible fill; cost is draw-call overhead). Fluid = 2 splat draws + 1 divergence + 2 Jacobi + 1 subtract + 2 advect = 6 full-quad passes over the dirty rectangle only, each with 4-5 texture taps. Display = 1 pass with 9 height taps (Sobel) + 1 colour tap. When nothing was splatted in the last 60 frames the simulation costs zero.
- [SRC] The app only redraws the painting when `needsRedraw` is set (simulation updated, resize, etc.). — [paint.js L618-L627](https://github.com/dli/paint/blob/6b8adfa226ecda14546c90b14a3d2a0d4898ad89/paint.js#L618-L627)

### Inferences
- [CALC] For an automatic (music-driven) painter the bristle PBD solver is optional: the reusable core is (i) capsule splats that add colour (alpha-lerp) + height (additive) + clamped velocity, (ii) a 2-Jacobi projection with strong velocity damping (0.8/frame) and no dye dissipation, (iii) dirty-rectangle scissoring with a 60-frame lifetime, (iv) Sobel-on-height + GGX shading. All of this is WebGL1-level and ports directly to WebGL2 (`RGBA16F` + `EXT_color_buffer_float`).
- [CALC] Because velocity decays by 0.8 per frame, after 60 frames it is 0.8^60 ~ 1.5e-6 of its initial value, so cutting the simulation off at 60 frames is visually lossless; this is the cheapest possible "drying" model (time-since-last-touch instead of a wetness field).
- [CALC] Drips under gravity could be added to this solver by adding `g * height` to velocity.y in the subtract pass where height exceeds a threshold; this is not in the source.

## 2. Pavel Dobryakov's WebGL-Fluid-Simulation and other WebGL "stable fluids" implementations; adapting them for viscous paint that stops and dries

### Takeaway
The whole solver is 8 small fragment shaders in one MIT-licensed file: curl -> vorticity confinement -> divergence -> pressure decay (x0.8) -> 20 Jacobi iterations -> gradient subtract -> advect velocity -> advect dye, with velocity on a 128-texel-short-side half-float grid and dye on a 1024-texel-short-side grid. For paint, keep the structure but drop vorticity, cut Jacobi to 2-4, make dissipation a per-pixel function of a wetness texture, and stop simulating regions that are dry (the David Li approach).

**Per-frame passes, in order** — [step() L1231-L1294](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation/blob/a2d292931f19d9b3b9f564e23e6c32729d2121c3/script.js#L1231-L1294); shaders [L746-L912](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation/blob/a2d292931f19d9b3b9f564e23e6c32729d2121c3/script.js#L746-L912)
- [SRC] 1. Curl: `w = 0.5 * (vR.y - vL.y - vT.x + vB.x)`.
- [SRC] 2. Vorticity confinement: `force = 0.5 * vec2(|wT| - |wB|, |wR| - |wL|); force /= length(force) + 0.0001; force *= curl * wC; force.y *= -1; v += force * dt; v = clamp(v, -1000, 1000)`.
- [SRC] 3. Divergence: `div = 0.5 * (R.x - L.x + T.y - B.y)` with reflecting walls (neighbour outside [0,1] -> use `-C`).
- [SRC] 4. Pressure "clear": `p *= PRESSURE (0.8)` — pressure is warm-started from the previous frame, decayed by 0.8, instead of being zeroed.
- [SRC] 5. Jacobi x 20: `p = (L + R + B + T - div) * 0.25`.
- [SRC] 6. Gradient subtract: `v -= vec2(pR - pL, pT - pB)`.
- [SRC] 7. Advect velocity (source = itself), 8. advect dye: `coord = vUv - dt * v(vUv) * texelSize; result = tex(source, coord); out = result / (1 + dissipation * dt)`. Velocity is therefore in sim-texels per second. With the defaults, [CALC] dye is multiplied by 1/(1+1/60) = 0.9836 per frame (half-life ~42 frames = 0.7 s) and velocity by 1/(1+0.2/60) = 0.9967 per frame (half-life ~208 frames = 3.5 s).
- [SRC] Splat (dye and velocity, same shader, one full-target pass each): `p = vUv - point; p.x *= aspect; out = base + exp(-dot(p,p)/radius) * color`, with `radius = correctRadius(SPLAT_RADIUS/100)` (x aspect if aspect > 1) i.e. Gaussian variance-like 0.0025 in UV^2; velocity splat "colour" = pointer delta (in UV) x `SPLAT_FORCE` 6000; random splats use dye colour x10 and velocity `1000*(rand-0.5)`. — [splat shader L726-L743](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation/blob/a2d292931f19d9b3b9f564e23e6c32729d2121c3/script.js#L726-L743), [splat() L1421-L1462](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation/blob/a2d292931f19d9b3b9f564e23e6c32729d2121c3/script.js#L1421-L1462)

**Per-frame cost**
- [CALC] At defaults: 25 passes on the sim grid (1 curl + 1 vorticity + 1 divergence + 1 clear + 20 Jacobi + 1 subtract + 1 velocity advect; each 2-5 taps) + 1 pass on the dye grid (advection) + 2 passes per splat (one on each grid). On a 16:9 canvas the sim grid is 228x128 = 29,184 texels, so the 25 sim passes touch ~0.73 M texels per frame; the dye grid is 1820x1024 = 1.86 M texels for the single dye-advection pass, which dominates. Bloom (prefilter + 8 down/up levels at 256) and sunrays (196) are post-effects and can be omitted.
- [SRC] Low-resolution simulation with a high-resolution dye field (bilinear sampling of the velocity texture from the dye pass) is the central performance device; no other throttling exists in the code.

**Adapting for viscous paint that stops moving and dries** (design derived from the two code bases; not present in either source)
- [CALC] Add one more ping-pong texture `wet` (R16F or pack with height: `RG16F` = wetness, height). Splat adds wetness = 1 along with pigment and velocity.
- [CALC] Per-pixel damping instead of the global `dissipation` uniform: in the velocity-advection pass sample wetness w and output `v * mix(0.0, k_fluid, smoothstep(w_min, w_max, w))` with k_fluid ~ 0.8-0.95 per frame (David Li uses 0.8, range 0.6-0.9). Dry pixels (w = 0) get velocity 0, so pigment there is no longer advected: it has "fixed".
- [CALC] Implicit viscosity (Stam's diffusion step) can be had with the same Jacobi shader form: `v' = (v0 + a*(vL+vR+vT+vB)) / (1 + 4a)` with `a = nu * dt / dx^2`, and nu made per-pixel `nu = nu0 / max(w, eps)` (viscosity rising as wetness falls). 2-4 iterations is enough at paint viscosities. [SEC: this is the standard formulation from Stam, "Stable Fluids" 1999; neither repository implements a diffusion step.]
- [CALC] Pigment advection must use dissipation 0 (Pavel: `DENSITY_DISSIPATION = 0`; Li: 1.0 multiplier) so paint never fades; and to stop numerical blurring of dry paint, mix: `pigment_out = mix(pigment_here, pigment_advected, mobility(w))`.
- [CALC] Drying: `w' = max(w - dryRate*dt, 0)` in the same pass (dryRate so that full-wet paint dries in N seconds; see section 8). Drips: add `gravity * w * height` to v.y where `w*height` exceeds a threshold.
- [CALC] Jacobi iterations: 2 (Li) is enough for viscous paint because the velocity field is heavily damped; 20 (Pavel) is tuned for swirling smoke/ink. Vorticity confinement (curl 30) should be 0 for paint; it creates smoke-like curls.
- [CALC] Skip-when-idle: track a dirty rectangle (Li) or a global "max wetness" flag; if nothing is wet, run zero simulation passes and only redraw when the composite changes.

### Inferences
- [CALC] A paint-tuned solver at sim 256 short side: (1 divergence + 3 Jacobi + 1 subtract + 1 velocity advect/damp + 1 wetness) = 7 sim passes ~ 0.8 M texel-writes on a 455x256 grid, plus 1-2 passes on the pigment grid. This is cheaper than Pavel's default (25 sim passes) and well inside an integrated-GPU budget; the display composite is likely the largest single cost.
- [CALC] The `PRESSURE: 0.8` warm start is a cheap way to get more effective Jacobi convergence from few iterations; worth keeping when cutting iterations to 2-4.

### Gaps
- The README contains no benchmark numbers; no frame-time measurements were found in the repository. "60 fps on a laptop" for these defaults is widely reported anecdotally but not documented in source.
- Other WebGL stable-fluids implementations (e.g. three.js-based ports) were not read line by line; they follow the same pass list.

## 3. Watercolour: Curtis et al. three-layer model, lattice-Boltzmann ink (MoXi), cellular-automaton watercolour, and open real-time implementations

### Takeaway
Two readable open implementations of Curtis et al. 1997 (C++ MIT; Rust MIT/Apache) agree on the update equations and on the paper's 12-pigment K/S table; both are CPU, offline-style (50 relaxation iterations per step) and neither is a real-time WebGL port. MoXi (lattice-Boltzmann D2Q9 with per-link "blocking" and "pinning") exists as an MIT Unity compute-shader port and an MIT/Apache Rust + WGSL port, and maps much more naturally to one or two fragment passes per frame. A single-file MIT C program shows the cheapest physically-flavoured option: a height-equalising cellular automaton over an active-cell list with CMY Beer-Lambert compositing.

Unity port uses 32x32 thread groups and 3 distribution textures exactly as this packing suggests.

### Inferences
- [CALC] For 60 fps WebGL2 the Curtis shallow-water solver is the wrong fit as published (50 Gauss-Seidel-style relaxations, staggered grid, adaptive sub-steps, per-glaze state). Its *pigment* rules are cheap and separable from the solver and can ride on any velocity field: the adsorption/desorption pair, the `p -= eta*(1 - blur(M))*M` edge term (one separable blur of the wetness mask at low resolution), and the capillary rule for back-runs. With a collocated stable-fluids grid (section 2) the edge term becomes "add `eta*(1 - blur(M))*M` to divergence" or equivalently add an outward velocity `v += k * grad(blur(M))` inside the wet mask.
- [CALC] MoXi is the better base for "ink/watercolour that spreads into wet areas and stops with a feathered edge": fixed cost, local stencil, natural wet-front pinning from a paper texture, and drying/fixing built in. Texture budget for WebGL2: 3 RGBA16F for distributions (ping-pong = 6), 1 RGBA16F for surface+flow water/ink scalars (x2), 1 RGBA16F fixed pigment (x2), 1 RGBA8 paper (grain, alum, pinning) ~ 11 textures at sim resolution; with multiple pigments, store pigment as RGB concentration (3 pigments, or CMY) per layer.
- [CALC] The CA approach (3c) is the only one here that is practical in a Canvas 2D fallback: with an active list and a 310x450 half-resolution grid it is a few tens of thousands of cell updates per sub-step in typed arrays.
- [CALC] The viscosity sign difference (3a) is most plausibly a literal transcription of the paper's printed formula in the C++ port versus a corrected (diffusive, +mu*laplacian) form in the Rust port; the + form is the physically stable one.

### Gaps
- The Curtis and Chu-Tai papers themselves were not re-read this session (grail.cs.washington.edu and ACM hosts not attempted); equations are as transcribed by the open implementations, cross-checked between two independent ports where both exist. The C++ repository bundles the paper PDF (`p421-curtis.pdf`) but it was not parsed.
- "Small's" 1991 cellular-automaton watercolour: no open port carrying that name was found; 3c is a CA in the same spirit, not a port of Small's rules.
- No open WebGL/GLSL port of the Curtis model with a meaningful user base was found; several 0-1-star 2026 repositories (e.g. Godot `Dubu911/Watercolor_simulation`, no licence) exist but were not read in depth.
- The values marked "tuned" in `jfernand/moxi-ink` are that author's fits, not published constants.

## 4. Cheap but convincing approximations used in generative-art code (polygon-deformation washes, wet-on-wet, edge darkening by blur difference, granulation, blooms)

### Takeaway
The dominant generative-art watercolour is the "Tyler Hobbs" polygon-deformation wash: 30-100 nearly transparent layers (alpha about 4-10 of 255) of a recursively midpoint-displaced polygon. The current state of the art in open code is p5.brush (MIT, WebGL2, actively updated to Nov 2026), which draws only 7 of a 20-step layer schedule into a half-float log-domain mask and then synthesises rim darkening, lost/wet edges, granulation on a procedural paper height, back-run blooms, pooling and pigment separation in one composite fragment shader, with wet-on-wet handled by a half-resolution "wet paper" buffer that decays by 0.45 per subsequent fill.

**4a. Classic polygon-deformation wash (Processing / p5)**
- [SRC] `sighack/watercolor-simulation` (Processing, MIT, 56 stars, commit `ac6781b`, Jan 2018): base shape = regular 10-gon of radius r; `deform(points, depth, variance, vdiv)` inserts, for each edge, a midpoint displaced by `randomGaussian() * variance` in x and y, recursing to `depth` with child variance `random(variance / vdiv)`. A wash is `base = deform(rpoly, 5, 15, 2)` then **100 layers**, each `deform(base, 5, random(r/10, r/4), 4)`, filled with **alpha 4/255** (`color(255, 0, 0, 4)`), no stroke. Multiple washes are **interleaved 5 layers at a time** (`stacklist_draw(stacklist, colors, 5)`) so colours mix rather than one simply covering the other. A paper "grid" texture is then overdrawn: diagonal white lines every 5 px, alpha `random(20, 50)`, stroke weight `1 + noise in [-0.5, 0.5]`, endpoints jittered +/-1 px by Perlin noise. — [watercolor.pde](https://github.com/sighack/watercolor-simulation/blob/ac6781b7487ad34191eaf0b1c1547cdf99ba24f9/watercolor.pde)

### Inferences
- [CALC] For a 60 fps automatic painter, do not redraw polygon stacks every frame. Use the p5.brush structure: (1) rasterise each new "stroke/wash event" once into a log-domain half-float mask (additive), (2) one separable half-resolution blur of the mask's dirty rectangle, (3) one composite pass over the dirty rectangle that computes rim, granulation, bloom and KM mixing and writes into the persistent canvas texture. Cost is per *event*, not per frame; frames with no new paint cost nothing.
- [CALC] "Wet-on-wet by blurring a wetness mask and advecting pigment along its gradient" as named in the brief: no repository read implements exactly that as a time-stepped rule; the closest are (i) Curtis' `(1 - blur(M))*M` pressure sink (pigment flows toward the wet boundary), (ii) p5.brush's static wet buffer that switches edges from hard to feathered. A time-stepped version consistent with both: `v = -k * grad(blur(W))` inside `W > 0`, then semi-Lagrangian advect suspended pigment with `v`, then fix pigment at rate proportional to water loss (MoXi rule). This is 3 cheap passes at half resolution.
- [CALC] "Edge darkening via difference of blurs": equivalent formulation to `outside = 2*(1 - blurInside)` above is `rim = clamp(k * (M - blur(M)), 0, 1)` for a binary/soft mask M; a second, narrower blur gives the crisp "pinned" line (p5.brush uses sigma and sigma/ratio in one pass).
- [CALC] "Salt" texture: none of the repositories read implements a named salt effect; the reticulation term (Worley cell walls gathering pigment, in patches) is the nearest analogue, and a salt look is the inverse (pale cells with dark walls at small scale).

## 5. Pigment mixing: Kubelka-Munk in code (spectral.js, libmypaint, Mixbox, GLSL ports) and the cheapest per-pixel formulation that turns blue + yellow green

### Takeaway
spectral.js is MIT and ships its own GLSL (`shader/spectral.glsl`); it up-samples sRGB to a 38-band reflectance with 7 fixed basis spectra, mixes K/S = (1-R)^2/(2R) linearly with concentration = factor^2 x tintingStrength^2 x luminance, and converts back. libmypaint (ISC) does a 10-band *weighted geometric mean* of reflectances (no K/S), which is cheaper. Mixbox is confirmed CC BY-NC 4.0 (non-commercial; not GPL-compatible) and must not be used. The cheapest formulation that still gives green from blue + yellow is a per-channel geometric mean in linear RGB (equivalently: store and add optical density, colour = paper x exp(-density)), at 3 `exp` per pixel.

- [CALC] Best quality that is still real-time in WebGL2: spectral.js K/S mixing with one side precomputed (p5.brush approach) or with a baked RGB->spectrum 3D LUT (Mixbox-Palette approach; a LUT can be generated from MIT spectral.js tables). ## 6. Oil / impasto: storing paint height, deriving normals, lighting, bristle furrows, and how thick paint is pushed and mixes in place (pickup, smear)

### Takeaway
Every open implementation read stores thickness as one scalar channel next to colour, derives the normal with a 3x3 Sobel on that channel, and lights it with a small Cook-Torrance/Blinn specular whose roughness falls as wetness rises. They differ in how paint moves: David Li advects colour+height with a damped fluid; an MIT WebGL2 simulator "IMPASTO" does it per stamp (8 upstream "smear" taps along the stroke motion, volume-weighted mixing in K/S space, a bristle "imprint" term that redistributes height); Krita keeps a separate 8-bit height layer stamped from the grey brush tip and only modulates lightness with it; libmypaint models pickup as a "smudge bucket" low-pass of sampled canvas colour.

## 7. Paper and canvas: generating grain / weave height maps and using them (dry-brush skipping, granulation, absorption)

### Takeaway
None of the real-time code bases ships a scanned paper texture as a requirement; they synthesise height from 3-6 octaves of hashed value noise plus an anisotropic "fibre" term, or a sine-product weave for canvas, and use the same height for four things: shifting where a wash edge stops, weighting pigment deposit (granulation), breaking up thin/dry strokes, and modulating absorption/drying or flow resistance.

### Cited Findings

## 8. Drying and fading: wetness decay, pigment fixing, "old paint fades back", and glazing vs alpha blending

### Takeaway
Open code uses three drying models: (1) a time-out (simulate each touched region for N frames, David Li: 60); (2) a wetness scalar decaying linearly or exponentially, slower where paint is thick or wetter, with pigment "fixed" in proportion to water lost (MoXi, the CA watercolour, IMPASTO); (3) a per-event counter (p5.brush: wetness x 0.45 per later fill). Glazing of dry layers is done either physically with Kubelka's layer formula or cheaply as multiplicative absorbance (`paper * exp(-density)`); ordinary alpha "over" is what the Processing-style sketches use and is what produces chalky, non-paint-like overlaps. No code read implements deliberate long-term fading of old paint.

### Inferences
- [CALC] Recommended wetness update for a per-frame pass at low resolution: `w' = max(0, w - dt * r0 * (a + b*paper) / (c + k*h))` (linear in time, faster on absorbent paper, slower for thick paint), with pigment fixing fraction `= waterLost / waterBefore` (MoXi/CA rule). Constants from code: r0 0.45/s, a 0.35, b 0.75 (watercolour); c 0.30, k 2.4 (oil).
- [CALC] "Old paint fades back" option (not found in any source): implement in *pigment-density space* so it looks like lightening rather than greying: `D' = D * exp(-dt / tau)` on the fixed-pigment density texture (tau tens of seconds to minutes), or blend the dry layer toward paper by a small factor only when global coverage exceeds a threshold; with the fluid-style formula this is `D / (1 + dissipation*dt)` using a dissipation of ~0.01-0.05 instead of 1. Because density is multiplicative on display (`exp(-D)`), fading in D space never produces the grey veil that alpha-fading toward white produces.
- [CALC] Two-buffer scheme for cheap glazing: `dry` density texture (RGB absorbance, updated only when a region dries) and `wet` layer (simulated). Display `paper * exp(-(D_dry + D_wet))`. Wet-on-dry strokes then glaze automatically (multiplicative); wet-on-wet strokes mix inside the wet layer before fixing.

### Gaps
- No open code implementing deliberate ageing/fading of dried paint (or re-wetting of dried watercolour beyond MoXi's blocking terms and Curtis' desorption) was found.
- Real drying-time constants for real media are not present in any repository; all constants are aesthetic.

## 9. Practical WebGL2 notes read from these code bases (float targets, fallbacks, ping-pong, low-resolution simulation, staying at 60 fps)

### Takeaway
The recurring recipe is: WebGL2 context without depth/stencil/antialias; `EXT_color_buffer_float` (or `EXT_color_buffer_half_float`) to render to RGBA16F; verify renderability by building a tiny FBO; `OES_texture_float_linear` only matters for 32F (16F is linearly filterable in WebGL2 core); ping-pong pairs with scissored dirty rectangles; simulation at a fraction of display resolution; and skip all passes when nothing is wet. One production-style project avoids float textures entirely (RGBA8 heat maps + 3D LUT).

### Inferences
- [CALC] Suggested buffer plan for the target app (derived, not from one source), all at sim resolution = display/2 except the canvas: `canvas` RGBA16F (dry pigment density RGB + height) at display or 0.75x; `wetA/B` RGBA16F (wet pigment density RGB + water); `velA/B` RG16F; `pressureA/B` R16F + `div` R16F (only if the fluid model is used); `paper` R8 tileable. With the low-res sim the per-frame fill cost is dominated by the single display composite.
- [CALC] Fallback ladder: (1) WebGL2 + EXT_color_buffer_float -> RGBA16F everywhere; (2) WebGL2 without float render targets -> RGBA8 heat-map model (Mixbox-Palette style: wetness, deposit, mask as 8-bit channels; colour mixing by geometric mean or LUT) — precision is adequate because those fields are bounded 0..1 and re-quantised every frame; (3) Canvas 2D -> active-cell CA on typed arrays at 1/2-1/4 resolution (section 3c) or pre-rendered polygon-stack washes (section 4a) drawn once per event, with `putImageData`/`drawImage` upscaling.
- [CALC] Audio safety: none of the code bases read coordinates rendering with audio. The low-cost choices that follow from them are: fixed sim step with at most one step per frame (Pavel clamp), event-driven deposit (cost scales with new strokes, not canvas size), and a hard cap on stamps/particles per frame (Mixbox-Palette's 15-120 stamps, 80-200 drips) so a dense musical passage cannot blow the frame budget.
- [SEC] In WebGL2, RGBA16F textures are filterable without extensions, while RGBA32F needs `OES_texture_float_linear`; rendering to either needs `EXT_color_buffer_float` (16F alone can also come from `EXT_color_buffer_half_float`). This is from the WebGL2/extension specifications (researcher's prior knowledge), consistent with how the sources query extensions but not stated verbatim in them.

### Gaps
- No repository publishes frame-time measurements on named hardware; "60 fps on an ordinary laptop" is supported only by pass-count arithmetic in these notes.
- Browser/device support percentages for `EXT_color_buffer_float` were not checked this session (non-GitHub hosts not queried).
- WebGPU ports (the two Rust crates use wgpu/WGSL) were not evaluated for browser use.
