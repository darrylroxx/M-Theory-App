## Key question 1 — For each open-source pitch tool: licence (SPDX, GPL-3.0-or-later compatibility), algorithm with constants, and LATENCY at 48 kHz

### Takeaway
The only open, purpose-built real-time vocal tuners are zita-at1/fat1 (GPL-2.0-or-later; FFT autocorrelation detector + resample-and-jump retuner; **1056 samples = 22.0 ms** at 48 kHz, or **160 samples = 3.3 ms nominal** in fat1's "Fast" mode) and Autotalent/TalentedHack (GPL-2.0-or-later; FFT autocorrelation/MPM + pitch-synchronous overlap-add with an optional LPC-lattice formant corrector; **2047 samples = 42.6 ms**). General-purpose shifters are all far slower: Rubber Band's live shifter states "50 ms or more", Signalsmith Stretch defaults to a 120 ms block, and none of the neural or vocoder-style tools (CREPE, WORLD) are low-latency designs.

#### 1.1 zita-at1 (Fons Adriaensen) and x42 fat1.lv2 (Robin Gareus) — read in full [SRC]
- **Licence:** `retuner.cc` header is "Copyright (C) 2009-2011 Fons Adriaensen … GNU General Public License … either version 2 of the License, or (at your option) any later version" → **GPL-2.0-or-later**, compatible with GPL-3.0-or-later. fat1's COPYING is the GPLv2 text. — [fat1.lv2 src/retuner.cc](https://github.com/x42/fat1.lv2/blob/master/src/retuner.cc); [fat1.lv2 COPYING](https://github.com/x42/fat1.lv2/blob/master/COPYING)
- fat1 states it is "an auto-tuner based on Fons Adriaensen's zita-at1"; "The only differences to zita-at1 is that the plugin reports its latency to the host, saves the state with the session and the MIDI input has sidechain semantics." Build deps: LV2 SDK, fftw. — [fat1.lv2 README](https://github.com/x42/fat1.lv2/blob/master/README.md)
- **Sizes by sample rate** (constructor): if fs < 64 kHz (44.1/48k): upsample ×2 (`_resampler.setup(1, 2, 1, 32)`, "32 is medium quality"), `_ipsize = 4096` (circular buffer, in upsampled samples), `_fftlen = 2048`, `_frsize = 128`. If fs < 128 kHz (88.2/96k): no upsampling, `_ipsize = 4096`, `_fftlen = 4096`, `_frsize = 256`. Else (192k): `_ipsize = 8192`, `_fftlen = 8192`, `_frsize = 512`. — [retuner.cc](https://github.com/x42/fat1.lv2/blob/master/src/retuner.cc)
- **Pitch range accepted:** "Accepted correlation peak range, corresponding to 60..1200 Hz": `_ifmin = _fsamp / 1200; _ifmax = _fsamp / 60;`. — [retuner.cc](https://github.com/x42/fat1.lv2/blob/master/src/retuner.cc)
- **Structure (verbatim comment):** "Pitch shifting is done by resampling the input at the required ratio, and eventually jumping forward or back by one or more pitch period(s). Processing is done in fragments of '_frsize' frames, and the decision to jump forward or back is taken at the start of each fragment. If a jump happens we crossfade over one fragment size. Every 4 fragments a new pitch estimate is made. Since _fftsize = 16 * _frsize, the estimation window moves by 1/4 of the FFT length." — [retuner.cc](https://github.com/x42/fat1.lv2/blob/master/src/retuner.cc)
- **Detector (`findcycle`)**, exact steps:
  1. Copy `_fftlen` samples from the circular buffer with stride `d = 2` when upsampled (so analysis is at the base rate), multiplied by a raised-cosine (Hann) window `0.5*(1 - cos(2*pi*i/_fftlen))`.
  2. (MOD build only) return "unvoiced" if `rms < _fftlen * 0.000031623f` — comment: "signal < -45dBFS/RMS".
  3. Forward real FFT (FFTW r2c); power spectrum `x*x + y*y` divided by `(1 + m*m)` with `m = i * fs / (fftlen * 3e3)` (a first-order roll-off at 3 kHz applied to the power spectrum); inverse FFT → autocorrelation.
  4. Normalise: `t = r[0] + 0.1f; r[i] /= (t * _fftWcorr[i])` where `_fftWcorr` is the normalised autocorrelation of the window itself (removes window bias).
  5. Skip the initial downslope in steps of 4 lags until the function rises; fail if that reaches `_ifmax`.
  6. From `max(i, _ifmin)` to `_ifmax` pick the lag `j` maximising `y * _fftWcorr[i]` subject to local maximum and **`y > 0.8f`** (voicing threshold on normalised autocorrelation).
  7. Parabolic refinement: `cycle = j + 0.5*(x - z)/(z - 2*y + x - 1e-9)` if `|z - 2y + x| > 2e-9`.
  — [retuner.cc](https://github.com/x42/fat1.lv2/blob/master/src/retuner.cc)
- **Voiced/unvoiced logic:** estimate every 4th fragment; on success `_count = 0`, `finderror()`. On failure: "the current ratio is kept for 5 fragments [estimates]. After that the signal is considered unvoiced and the pitch error is reset" (`++_count > 5` → `_cycle = _frsize; _voiced = false; _error = 0`), and "Bias is removed after two unvoiced fragments" (`_count == 2` → `_lastnote = -1`). — [retuner.cc](https://github.com/x42/fat1.lv2/blob/master/src/retuner.cc)
- **Note choice and correction speed (`finderror`)**: `f = log2(fs / (cycle * refpitch))` (octaves relative to A); for each of 12 notes enabled in the 12-bit `_notemask`, `d = f - (notescale[i] - 9)/12`, wrapped to ±0.5 octave; the last-used note gets its distance reduced by `_notebias`; nearest wins. If the note is unchanged: `_error += _corrfilt * (dm - _error)` (one-pole smoothing); on a note change the error **jumps** (`_error = dm`). Then `_ratio = pow(2, _corroffs/12 - _error * _corrgain)`. — [retuner.cc](https://github.com/x42/fat1.lv2/blob/master/src/retuner.cc)
- **Parameter scaling (retuner.h):** `set_notebias(v): _notebias = v / 13.0f`; `set_corrfilt(v): _corrfilt = (4 * _frsize) / (v * _fsamp)` (v is a time in seconds; coefficient is per pitch-estimate tick); `set_corrgain(v)`; `set_corroffs(v)` (semitones); `set_notescale(i, v): _notescale[i] = i + v` (per-note microtuning); `get_error()` returns `12 * _error` (semitones). — [fat1.lv2 src/retuner.h](https://github.com/x42/fat1.lv2/blob/master/src/retuner.h)
- **Control ranges/defaults (LV2 ttl):** Tuning 400–480 Hz (default 440); Bias 0–1 (default 0.5); Filter 0.02–0.5 (default 0.1); Correction 0–1 (default 1.0); Offset −2…+2 (default 0); Pitch Bend Range 0–7 (default 2); Fast Correction 0/1 (default 0); 12 per-note enables. — [fat1.lv2 lv2ttl/](https://github.com/x42/fat1.lv2/tree/master/lv2ttl)
- **Retuner details:** read pointer starts at `_ipsize / 2` behind the write pointer; output is 4-point cubic interpolation of the (2× upsampled) buffer advancing by `dr = _ratio` (×2 when upsampled); crossfade function is "half of raised cosine" over one fragment (`_xffunc[i] = 0.5*(1 - cos(pi*i/_frsize))`). At each fragment boundary: `dr = _cycle * ceil(_frsize / _cycle)` ("A jump must correspond to an integer number of pitch periods, and to avoid reading outside the circular input buffer limits it must be at least one fragment size"); `ph = (r1 - _ipindex wrapped)/_frsize + 2*_ratio - 10`; if unvoiced → crossfade back to the nominal position ("reset playhead position and crossfade to avoid jitter and get a consistent output latency"); else if `ph > 0.5` jump **back** by `dr` and crossfade; else if `ph + dp < 0.5` (dp = dr/_frsize) jump **forward** by `dr` and crossfade. — [retuner.cc](https://github.com/x42/fat1.lv2/blob/master/src/retuner.cc)
- **Fast mode (fat1 addition):** "Fast mode allows outputting the signal before the pitch has been computed, resulting in a lower latency at the cost of a small delay between the correction and the pitch analysis. This is useful in live situation." Implemented as a read-ahead offset `_readahead = _ipsize * 7 / 16` added to the read index, crossfaded in/out over one fragment. — [retuner.cc](https://github.com/x42/fat1.lv2/blob/master/src/retuner.cc)
- **Reported latency (fat1.cc):** `rate < 64000 → latency = 1024`; `< 128000 → 2048`; else `4096`; in Fast mode the port reports `latency / 8`; and "add 32 samples for resampler's latency" when upsampling. — [fat1.lv2 src/fat1.cc](https://github.com/x42/fat1.lv2/blob/master/src/fat1.cc)
- **[CALC] Latency table from those lines:**

  | Rate | Normal | Fast |
  |---|---|---|
  | 44.1 kHz | 1024+32 = 1056 samples = 23.9 ms | 128+32 = 160 samples = 3.63 ms |
  | 48 kHz | 1056 samples = **22.0 ms** | 160 samples = **3.33 ms** |
  | 96 kHz | 2048 samples = 21.3 ms | 256 samples = 2.67 ms |
  | 192 kHz | 4096 samples = 21.3 ms | 512 samples = 2.67 ms |

- **[CALC] Timing at 48 kHz:** fragment = 128 samples = 2.67 ms (also the crossfade length); pitch estimate every 4 fragments = 512 samples = 10.7 ms; analysis window = 2048 base-rate samples = 42.7 ms; circular buffer = 2048 base-rate samples. Correction filter coefficient at default Filter = 0.1 s: (4·128)/(0.1·48000) = 0.107 per 10.7 ms tick (time constant ≈ 0.1 s); at minimum 0.02 s: 0.533 per tick. Bias default 0.5 → 0.5/13 = 0.038 octave ≈ 0.46 semitone of hysteresis toward the previous note.

#### 1.2 Autotalent 0.2 (Tom Baran) and TalentedHack (Jeremy Salwen) — read [SRC]
- **Licence:** `autotalent.c` header: "Free software by Thomas A. Baran … VERSION 0.2 March 20, 2010 … GNU General Public License … either version 2 of the License, or (at your option) any later version" → **GPL-2.0-or-later**. — [autotalent.c (copy in PyAutoTune)](https://github.com/ederwander/PyAutoTune/blob/master/autotalent.c)
- TalentedHack: `talentedhack.c` header is GPL v2-or-later ("VERSION 1.82 Jul 30, 2010 … Based on Autotalent"); the repo LICENSE file is the GPLv3 text. Either way compatible with GPL-3.0-or-later. — [TalentedHack talentedhack.c](https://github.com/jeremysalwen/TalentedHack/blob/master/talentedhack.c); [TalentedHack LICENSE](https://github.com/jeremysalwen/TalentedHack/blob/master/LICENSE)
- **Buffer sizes:** `cbsize = 4096` if SampleRate ≥ 88200 else `2048`; `corrsize = cbsize/2 + 1`; `noverlap = 4` ("Every N/noverlap samples, run pitch estimation / manipulation code"). — [autotalent.c](https://github.com/ederwander/PyAutoTune/blob/master/autotalent.c); [TalentedHack circular_buffer.c](https://github.com/jeremysalwen/TalentedHack/blob/master/circular_buffer.c)
- **Latency:** "Tell the host the algorithm latency": `*(m_pfLatency) = (N-1)` → 2047 samples at 44.1/48 kHz, 4095 at ≥88.2 kHz. — [autotalent.c](https://github.com/ederwander/PyAutoTune/blob/master/autotalent.c); same line in [talentedhack.c](https://github.com/jeremysalwen/TalentedHack/blob/master/talentedhack.c)
- **[CALC]** 2047 samples = **42.6 ms at 48 kHz** (46.4 ms at 44.1 kHz); 4095 samples = 42.7 ms at 96 kHz. Pitch update every 512 samples = 10.7 ms at 48 kHz.
- **Autotalent detector:** analysis window is "a single raised cosine from N/4 to 3N/4" (`cbwindow[i + cbsize/4] = -0.5*cos(4*PI*i/(cbsize-1)) + 0.5`, zero elsewhere); FFT (mayer_fft) → remove DC → magnitude squared → IFFT → normalise by lag 0 ("autocovariance"). "Pitch period is determined by the location of the max (biased) peak within a given range; Confidence is determined by the corresponding unbiased height" (`conf = peak * acwinv[lag]`, acwinv = inverse of the window's autocorrelation). Range `pmax = 1/70 s`, `pmin = 1/700 s` (70–700 Hz, "eventually may want to bring these out as sliders"); refinement is a 3-point centre of mass; voiced threshold `vthresh = 0.7` ("The voiced confidence (unbiased peak) threshold level"); pitch is only updated when voiced. — [autotalent.c](https://github.com/ederwander/PyAutoTune/blob/master/autotalent.c)
- **TalentedHack detector:** "MPM Algorithm, thanks to Philip McLeod, and Geoff Wyvill, adapted from their GPL Tartini program"; same windowed FFT autocorrelation with `noise_floor = 0.05` ("To prevent rounding errors when quiet") in the normalisation; walks to the second zero crossing, collects the highest peak between successive positive zero crossings, then picks the **first** key maximum ≥ `mpm_k × highest peak`; parabolic interpolation; confidence = peak × acwinv. Port defaults: min pitch 70 Hz, max pitch 700 Hz, voiced threshold 0.7 (0–1), `mpm_k` 0.9 (0.5–1.0), pitch-pull 0, pitch-smooth 0 (0–0.5), formant correction 0 (off), formant warp 0 (−1…1), mix 1. — [TalentedHack pitch_detector.c](https://github.com/jeremysalwen/TalentedHack/blob/master/pitch_detector.c); [talentedhack.ttl](https://github.com/jeremysalwen/TalentedHack/blob/master/talentedhack.ttl)
- TalentedHack README: differences from Autotalent include "Slightly more accurate pitch detection (Uses MPM method instead of straight autocorrelation)", "It uses FFTW for the DFT routines", "It separates the pull to semitone and snap to scale functionality", MIDI in/out, and "**The formant corrector is broken :(**"; also "it has difficulty detecting low notes. I think this might be remedied by increasing the buffer size of the pitch detector. Anyway, the same problem is present in the original." — [TalentedHack readme.md](https://github.com/jeremysalwen/TalentedHack/blob/master/readme.md)
- **Pitch shifter (both):** comment "Pitch shifter (kind of like a pitch-synchronous version of Fairbanks' technique). Note: pitch estimate is naturally N/2 samples old". Two phase accumulators: `inphinc = 1/(input period in samples)`, `outphinc = 1/(output period)`, `phincfact = outphinc/inphinc`. "When input phase resets, take a snippet from N/2 samples in the past"; "When output phase resets, put a snippet N/2 samples in the future" — the fragment is resampled by `phincfact` with a 3rd-degree polynomial interpolator ("based on eqns from Hal Chamberlin's book"), Hann-windowed (window stretched to the grain length) and overlap-added into an output ring buffer. Output pitch is clamped (`if (outpitch<-36) outpitch = -48; if (outpitch>24) outpitch = 24;` semitones re A). — [TalentedHack pitch_shifter.c](https://github.com/jeremysalwen/TalentedHack/blob/master/pitch_shifter.c); [autotalent.c](https://github.com/ederwander/PyAutoTune/blob/master/autotalent.c)
- **Formant corrector (both):** "Somewhat experimental formant corrector: formants are removed using an adaptive pre-filter and re-introduced after pitch manipulation using post-filter". Constants: `ford = 7` ("should be sufficient to capture formants"); `falph = pow(0.001, 80/fs)`; `flamb = -(0.8517*sqrt(atan(0.06583*fs)) - 0.1916)` ("or about -0.88 @ 44.1kHz" — a frequency-warping all-pass coefficient); `flpa = pow(0.001, 10/fs)`; `fmutealph = pow(0.001, 1/fs)`; a first-difference "highpass pre-emphasis filter" before and a "lowpass post-emphasis filter" after; an adaptive lattice per order (running `sig`, `k`, smoothed reflection coefficient stored per sample); the post-filter is run three times per sample "because of a pesky delay free loop" (0-response, 1-response, then solve); formant warp: `f = pow(2, Fwarp/2)*(1+flamb)/(1-flamb); frlamb = (f-1)/(f+1)`. — [TalentedHack formant_corrector.c](https://github.com/jeremysalwen/TalentedHack/blob/master/formant_corrector.c); [autotalent.c](https://github.com/ederwander/PyAutoTune/blob/master/autotalent.c)
- TalentedHack pitch smoother: slews toward the target with `maxdiff = 0.04` semitones dead-band, rate set by `pitchsmooth × periods_per_second` where `periods_per_second = fs*noverlap/N`. — [TalentedHack pitch_smoother.c](https://github.com/jeremysalwen/TalentedHack/blob/master/pitch_smoother.c)

- **Why zita's normal latency is 1024 samples:** the audio delay (`_ipsize/2` = 1024 base-rate samples) equals half of the 2048-sample analysis window, so each output sample is corrected with a pitch estimate whose window is centred on it. Fast mode removes 7/8 of that delay; the correction then lags the audio by roughly 19–30 ms (half-window minus 128 samples, plus up to one 10.7 ms estimate interval). That lag behaves like a built-in minimum "retune speed" and is why the code calls it "a small delay between the correction and the pitch analysis".
- **Fast-mode latency is nominal, not constant.** From the jump logic (`ph > 0.5` → jump back; `ph + dp < 0.5` → jump forward; jump = integer pitch periods ≥ one fragment) the read pointer floats between about 0.5 fragment and 0.5 fragment + one jump behind the nominal point while a correction is active. In Fast mode that is ≈ 64 samples up to 64 + (one jump) samples: for a 200 Hz note (240-sample period) ≈ 1.3–6.3 ms; for an 80 Hz note (600-sample period) ≈ 1.3–13.8 ms; it returns to 128 samples (+32 resampler) whenever the signal is unvoiced. This matches the SOS observation that a commercial live tuner's latency "varies between 0 and 4 ms depending on the frequency of the current note": period-jump retuners inherently have a delay that wanders by up to one pitch period.
- **Low male voice (80 Hz):** period = 12.5 ms = 600 samples at 48 kHz. Autocorrelation-family detectors (YIN, MPM, zita) need at least two periods in the window → ≥ 25 ms / 1200 samples; zita uses 2048 (3.4 periods at 80 Hz; its floor is 60 Hz = 800-sample lag). Autotalent/TalentedHack use an *effective* 1024-sample window (the raised cosine only spans the middle half of the 2048 buffer) = 1.5 periods at 70 Hz, which explains the README's "difficulty detecting low notes". A detector therefore cannot respond to a new low note in less than ~20–25 ms no matter how short the audio path is; only the audio path can be made short (as fat1 Fast does).
- **Formant behaviour:** zita/fat1 shift formants with pitch. For true correction (typically well under ±1 semitone, i.e. < 6% formant shift) that is inaudible in practice and is why zita sounds clean; for hard-tune jumps of several semitones or for harmonies (thirds/fifths) the "chipmunk" shift becomes audible and a PSOLA-type or envelope-corrected method is needed. Autotalent's grain OLA re-uses resampled grains too (it resamples each fragment by `phincfact`), which is why it needs the separate lattice formant corrector.
- **Minimum latencies by method (order of magnitude, 48 kHz):** resample-and-jump (zita Fast) ≈ 3 ms nominal + up to one period; TD-PSOLA ≈ one to two periods of the lowest note (12–25 ms at 80 Hz) plus pitch-marking; phase vocoder ≈ one analysis window (20–120 ms; 50 ms+ for Rubber Band live); WORLD/neural ≈ tens of ms and heavy CPU.
- **Port effort for the zita retuner in Rust:** ~500 lines of C++; needs one real FFT of 2048 (e.g. `realfft`/`rustfft`, MIT/Apache) twice per 512 samples, a 2× interpolator at 44.1/48 kHz (zita uses its own resampler with filter half-length 32; any half-band polyphase FIR will do), a 4096-sample ring buffer and a 4-point cubic interpolator. CPU cost is negligible. The 12-bit note mask and per-note microtuning map directly onto an app that already knows the song key/scale.

## Key question 2 — What is the lowest-latency credible pitch-correction design, is it acceptable in a ~8 ms round-trip monitoring chain, and how should it be offered?

### Takeaway
The lowest-latency credible open design is the zita-at1 retuner with fat1's read-ahead ("Fast") mode: about 3.3 ms nominal added delay at 48 kHz, wandering by up to one pitch period while it corrects, with the pitch decision itself still 20–30 ms behind the voice. That is usable as an **opt-in "tuned monitoring" mode with its latency stated**, but it should not sit in the default zero-latency path; best-quality tuning, formant-preserving shifts and harmonies belong in an **offline pass on the recorded take**.

### Cited Findings
- fat1 Fast mode reports `latency/8` (+32 samples for the 2× resampler): 160 samples at 48 kHz; normal mode 1056 samples. — [fat1.cc](https://github.com/x42/fat1.lv2/blob/master/src/fat1.cc)
- The code's own description of the trade-off: "lower latency at the cost of a small delay between the correction and the pitch analysis. This is useful in live situation." — [retuner.cc](https://github.com/x42/fat1.lv2/blob/master/src/retuner.cc)
- Autotalent-family latency is N−1 = 2047 samples and "pitch estimate is naturally N/2 samples old". — [autotalent.c](https://github.com/ederwander/PyAutoTune/blob/master/autotalent.c)
- Rubber Band's purpose-built live shifter is "still not a low-latency effect, with a delay of 50ms or more". — [RubberBandLiveShifter.h](https://github.com/breakfastquay/rubberband/blob/default/rubberband/RubberBandLiveShifter.h)
- A leading commercial live tuner has 0–4 ms plug-in latency that depends on note frequency, reports zero to the host, and still required a 64-sample buffer for comfortable monitoring in the reviewer's test. — [SOS: Waves Tune Real-Time](https://www.soundonsound.com/reviews/waves-tune-real-time)
- The SOS reviewer on tracking with tuning: "in a recording session, I'm not sure I'd generally want to track with pitch-correction in my signal chain but, if it is something you need — perhaps as a special effect or to provide a bit of a comfort blanket to an insecure singer — [it] can do it." — [SOS: Waves Tune Real-Time](https://www.soundonsound.com/reviews/waves-tune-real-time)
- Hard-tune genres do monitor through tuning while recording, with the tuner first in the monitoring chain followed by delay and reverb, and the take recorded dry on a separate track ("anything I put on, plug-in-wise, is not printed on the record track, but you are still able to hear the effects in real time while recording"). — [SOS Inside Track (hip-hop vocal chain)](https://www.soundonsound.com/techniques/inside-track-future-draco)
- Conventional advice for natural singing is to tune after recording, not in the headphones. — [SOS Vocal Recording & Production Masterclass](https://www.soundonsound.com/techniques/vocal-recording-production-masterclass)
- Signalsmith notes its formant correction "is not a sharp as monophonic algorithms (such such as PSOLA)" — i.e. for a solo voice, a monophonic pitch-synchronous method is the quality reference. — [signalsmith-stretch README](https://github.com/Signalsmith-Audio/signalsmith-stretch)
- Pitch-corrected or pitch-shifted copies are also used as *effects feeds* rather than on the dry voice: "try using pitch correction on the reverb feed … so that the reverb sound is just slightly different in pitch"; and stereo delays whose returns are detuned "by eight cents" up on one side and down on the other add width without changing the average pitch. — [SOS Vocal FX](https://www.soundonsound.com/techniques/vocal-fx); [SOS Mix Rescue: Mixing Metal](https://www.soundonsound.com/techniques/mix-rescue-mixing-metal) [SEC for the 8-cent figure]

### Inferences
- **Latency budget [CALC]:** with an ~8 ms round trip, tuned monitoring via a zita-Fast port gives ≈ 11.3 ms nominal (8 + 3.33), rising transiently toward ≈ 14–22 ms on low notes while the read pointer is a pitch period late; zita normal mode gives ≈ 30 ms; an Autotalent-style engine ≈ 51 ms; Rubber Band live ≥ 58 ms. Only the first is plausible for singing along to oneself; the 30 ms+ options are heard as a slap/doubling against bone-conducted sound and are unsuitable for monitoring.
- **Recommended product shape (three tiers):**
  1. **Default monitoring path: no pitch processing, zero added latency.** "Vocal alteration" that is free of dry-path latency: doubler/widener and chorus built from short modulated delays on a parallel wet path (the dry voice stays undelayed), micro-detuned stereo delays (±5–8 cents), octave-up shimmer *inside the reverb/delay feed* (latency is irrelevant there because the feed is already delayed), and a channel vocoder driven by the app's chords (IIR filter-bank vocoders have no block latency; Calf and TAL-Vocoder-2 are open references).
  2. **Optional "Tuned monitoring" toggle, labelled with its delay** (e.g. "adds ~3 ms, pitch follows after ~25 ms"): port of the zita retuner in Fast mode. Record the dry signal; apply tuning non-destructively. Drive the 12-note mask from the song's key/scale (and optionally the current chord), expose only "Amount" (`_corrgain` 0–1), "Speed" (`_corrfilt` 0.02–0.5 s; add a 0 = hard-tune option that bypasses the filter) and perhaps "Stickiness" (`_notebias`). When the toggle is on, the monitoring path must be 100% wet (mixing tuned and dry-direct signals combs), so hardware direct monitoring has to be off.
  3. **Offline "Tune take" on recorded audio (best quality, no latency constraint):** long-window F0 tracking (MPM/pYIN-style with a 2048–4096-sample window and smoothing across frames), note segmentation against the key, correction curve with adjustable speed/amount and vibrato preservation, then synthesis either with the zita retuner in normal (time-aligned) mode for small corrections, or a pitch-synchronous (PSOLA-type) / envelope-compensated shifter for large shifts, formant control and **harmonies**. Because it is offline, look-ahead is free, so note onsets can be corrected from their first cycle (impossible live).
- **Harmonies / formant shifting live** are not achievable near zero latency with any open method found: they need either PSOLA (≥ 1–2 periods + pitch marking) or a vocoder (≥ one window). Offer them offline, or in the tuned-monitoring mode only with an honest 20–45 ms figure (Autotalent-class).
- **Do not use AGPL `tdpsola`**; a TD-PSOLA synthesis stage is simple enough to write from the literature, and Autotalent's GPL-2.0-or-later grain shifter is a compatible reference for the pitch-synchronous overlap-add bookkeeping.
- Neural detectors (CREPE/PENN) are attractive only for the offline pass (robust F0 on breathy/noisy takes); they bring a model file and an inference runtime and offer nothing for latency.

### Gaps
- No sourced perceptual threshold for "acceptable" vocal self-monitoring delay was retrieved in this session (the only data point is the SOS reviewer moving from 256- to 64-sample buffers). The acceptability judgement above is an engineering inference; the report writer should cross-check with the latency notes already in `Scarlet Solo and vocal chain DSP/scarlet_drivers_latency_engine.md`.
- The fast-mode delay wander (0.5 fragment … +1 jump) is derived by reading the jump logic, not measured; it should be confirmed with an impulse/sine test of the port.
- How commercial "Live/Low Latency" modes achieve sub-millisecond figures is not documented in anything I could read; vendor numbers lack buffer/host conditions.

## Key question 3 — Best-practice module order for a vocal strip, and a table of genre presets with concrete targets

### Takeaway
Across open strips, commercial suites and engineers' documented chains the stable pattern is: level/clean-up first (auto-level, high-pass, gate), then (optional) pitch, de-ess, corrective EQ, one or two compressors (fast peak control → slow levelling), tonal EQ, saturation, then time-based effects on parallel sends (delay → reverb, returns filtered and optionally ducked by the dry vocal), with −18 dBFS as the internal reference level. De-esser placement and EQ-before/after-compression are genuinely debated; a strip should fix a sensible default (de-ess before compression, with the "air" boost after compression followed by a light second de-ess) rather than expose routing.

### Cited Findings

Expander: threshold "around -45 to -60 dB" with "1:4 or 1:10". [SRC] — [SOS: How To Make Your Vocals Twice As Good, Part 2](https://www.soundonsound.com/techniques/how-make-your-vocals-twice-good-part-2)
- EQ landmarks (male voice): lows "below about 150-200 Hz" (high-pass 12 dB/oct, 6 or 18 as needed); low-mid mud "around 300-400 Hz" (slight broad cut); intelligibility "2.5-4.5 kHz"; "air" from "5-6 kHz" upward (shelf), or "a parametric boost in the 4-7 kHz range, with a wide Q" when a shelf adds hiss. Airy gloss: "the merest broad boost at 12kHz". [SRC] — [SOS: Vocals Twice As Good, Part 2](https://www.soundonsound.com/techniques/how-make-your-vocals-twice-good-part-2); [SOS Vocal FX](https://www.soundonsound.com/techniques/vocal-fx)
- De-esser band: "frequencies in the sibilance range (typically 3-6kHz)"; simple wide-band de-essers "can impart a lisping quality"; the best "attenuate only frequencies in the sibilance band". Breath control: a gate with "attenuation when closed … around 6dB, rather than having it mute everything". [SRC] — [SOS Masterclass](https://www.soundonsound.com/techniques/vocal-recording-production-masterclass)
- Metal mix example: vocal already printed "with nearly 20dB of carefully constructed series compression", so mix compression was "5-6 dB"; sibilance "at around 9.3kHz" de-essed by "7-8 dB … on sibilant peaks"; HPF at 80 Hz; cuts at 608 Hz and 3.77 kHz; +1.2 dB at 140 Hz; shelf +2.3 dB at 6.8 kHz and +3.1 dB at 10 kHz; "parallel distortion … Only the subtlest introduction". Tracking compression suggestion for heavy vocals: about 4:1, attack under 3 ms, 6–8 dB on the loudest notes [SEC]. Another metal rescue needed "three compressors in series, registering a total of 20dB gain reduction" plus two-band compression split at 1.15 kHz with ratios 1.19:1/1.27:1. [SRC] — [SOS: Making Modern Metal, Part 3](https://www.soundonsound.com/techniques/making-modern-metal-part-3); [SOS Mix Rescue: Mixing Metal](https://www.soundonsound.com/techniques/mix-rescue-mixing-metal); [SOS: Making Modern Metal, Part 2](https://www.soundonsound.com/techniques/making-modern-metal-part-2) (tracking-compression figure, via search summary)
- Parallel compression: feeding the vocal to several different compressors at once and blending gives both level control and tone; distortion processors, limiting and clipping can take a compressor's place in the parallel set; a heavily squashed parallel bus fed a little vocal is used in a classic-rock rescue. [SRC] — [SOS: Advanced Vocal Compression](https://www.soundonsound.com/techniques/advanced-vocal-compression); [SOS Mix Rescue: Classic Rock](https://www.soundonsound.com/techniques/mix-rescue-classic-rock-production)

#### 3.4 Reverb/delay send practice (numbers)
- "Don't put your reverb plug-in directly on the vocal channel … create a new auxiliary (bus) track … Set it to 100% wet"; "add reverb after compression and through a send"; pre-delay "Start … around 20–30 ms. If your song has a strong rhythmic pulse, try adjusting pre-delay to match the tempo". [SRC] — [UA: How to Use Reverb on Vocals](https://www.uaudio.com/blogs/ua/how-to-use-reverb-on-vocals)
- "a typical vocal reverb treatment might comprise a plate reverb emulation with a decay time of 1.2 seconds or so and a pre-delay of 60-80ms." [SRC] — [SOS: Choosing The Right Reverb](https://www.soundonsound.com/techniques/choosing-right-reverb)
- "Vocal plate reverbs rarely need to be longer than 1.8 to 2.5 seconds, and in many cases rolling off some low end below 200Hz gives a cleaner and more lively sound. Putting a subtle repeating delay before the plate reverb can also produce a nice effect". Plate plus a short ambience, balanced, covers "a fairly upfront and focused vocal to a long ballad reverb". [SRC] — [SOS Masterclass](https://www.soundonsound.com/techniques/vocal-recording-production-masterclass)
- Upfront vocal: "add between 50 and 80mS of pre-delay"; "the faster and denser the track, the shorter the reverb decay time needs to be". **Ducking:** "ducking the reverb output when the dry vocal part is sounding … It's probably only necessary to duck the reverb level by 3dB or so … start with values in the 250-500mS range" for attack/release. [SRC] — [SOS: Advanced Reverberation, Part 2](https://www.soundonsound.com/advanced-reverberation-0)
- Ducked delay recipe: compressor after the delay on the return, side-chained from the dry vocal, "Ratio to 2:1 and the Release control to about 150ms", attack zero, auto-gain off, lower the threshold until the delay ducks. Also: a gate before the reverb with low cut ≈ 7 kHz, attack/release 1 ms, hold 50 ms, inverted range, to keep "S" sounds out of the reverb. [SRC] — [SOS: Logic — Dynamics Processing With Reverb/Delay](https://www.soundonsound.com/techniques/logic-dynamics-processing-reverbdelay)
- A plate preset documented by UA: pre-delay 87 ms ("Anywhere between 70ms and 180ms is a reasonable range"), decay 2.5 s ("the classic starting point" for a lead vocal), treble damping to bring the HF decay to about one second, low cut "up to 180Hz"; "Send the delay return into the plate's aux channel, so the reverb is processing the delay's repeats". [SRC] — [UA: Pure Plate vocal preset](https://www.uaudio.com/blogs/ua/peter-mokran-vocal-preset-uad-pure-plate)
- "Abbey Road" send EQ: high-pass about 600 Hz and low-pass about 10 kHz around the reverb; a common variant lowers the top cut to 6 kHz; other guides suggest return HPF 250 Hz / LPF 7 kHz. The historical attribution is folklore in the sources found. [SEC] — [Soundfly](https://flypaper.soundfly.com/produce/the-abbey-road-trick-how-to-eq-reverb-sends-to-free-up-space-in-a-mix/); [Sage Audio](https://www.sageaudio.com/articles/how-to-mix-vocal-reverb)
- Metal vocal effects set: plate "1.2s decay and no pre-delay" + a "slapback reverb" (1.6 s room with "an eighth-note pre-delay", 159 ms at 189 bpm); mono slapback delay; quarter-note delay each side with "one side [increased] by 5ms and … the other [lowered] by the same amount", moderate feedback, low and high cuts and tape emulation on the return; a half-note / dotted-half delay with strong feedback, low-passed and distorted; short ambience with "a pre-delay of 15ms to reduce comb-filtering". [SRC] — [SOS: Making Modern Metal, Part 3](https://www.soundonsound.com/techniques/making-modern-metal-part-3); [SOS Mix Rescue: Mixing Metal](https://www.soundonsound.com/techniques/mix-rescue-mixing-metal)
- Slapback: early-reflection cluster "between 70 and 110ms", reverb time under half a second, level "around 60 percent of the dry level", plus a sharp low cut "at around 200Hz"; tape at 15 ips "usually gives a nice slapback". Tape echo "gets warmer and less distinct every time the sound is fed back … which makes the delay sit further back in the mix". Telephone effect: band-limit "roughly between 250Hz and 2kHz" with steep filters. Shimmer: "pitch-shift the audio up an octave before feeding it to a delay or reverb". [SRC] — [SOS Vocal FX](https://www.soundonsound.com/techniques/vocal-fx)
- Slapback ranges from other guides: about 80–140 ms with no feedback; 50–150 ms; a little modulation for tape character. [SEC] — [Yamaha: Using Delay, Part 1](https://hub.yamaha.com/proaudio/recording/using-delay-part-1); [Sweetwater](https://www.sweetwater.com/insync/supercharge-your-vocals-with-delay-processing/)
- Rap leads are usually drier than pop: "a small plate with a short decay", a slap at 80–120 ms or a synced 1/8 or 1/4 kept low; compression figures quoted range from 4–8 dB on the loudest phrases at 3:1–4:1 to "at least 10 dB" at 8:1. [SEC] — [Violet Recording](https://violetrecording.com/how-to-mix-rap-vocals/); [Music Guy Mixing](https://www.musicguymixing.com/how-to-mix-rap-vocals/)
- A pop mix template: hall, plate and long reverbs plus half-, quarter- and eighth-note delays available as sends. [SEC] — [SOS Inside Track (pop template)](https://www.soundonsound.com/techniques/inside-track-justin-bieber-purpose)
- Reverb type by style: "synthetic digital reverb and plate reverb … are still the first choices for most pop work"; "convolution reverbs can work well on folk or jazz music, where you expect to hear the music performed in a specific type of environment"; spring is the classic guitar/retro colour. [SRC] — [SOS: Choosing The Right Reverb](https://www.soundonsound.com/techniques/choosing-right-reverb)

#### 3.5 Gain staging
- Many analogue-modelled processors are calibrated so "0 VU" = −18 dBFS; working practice: set each track to play "roughly around -18 dBFS", "maybe -20 dBFS, so that I have more headroom as I stack plug-ins"; "Levels should hover around -18 dBFS for average signal strength in digital systems". [SRC] — [iZotope: Gain staging](https://www.izotope.com/en/learn/gain-staging-what-it-is-and-how-to-do-it.html)
- "the correct threshold setting always depends on the level and dynamics of the signal being processed" — presets cannot work without level normalisation. [SRC] — [SOS Masterclass](https://www.soundonsound.com/techniques/vocal-recording-production-masterclass)

### Inferences

#### 3.6 Recommended strip order (mono in → stereo out)
1. **Input trim + auto-level to −18 dBFS RMS** (slow, gated RMS follower; Nectar puts Auto-Level first). This is what makes one preset work across singers: every threshold downstream is then relative to a known level. Zero latency.
2. **High-pass** (12 dB/oct, 70–120 Hz) — removes proximity/rumble before anything is level-dependent. Zero latency (IIR).
3. **Gate / downward expander** (threshold −45…−60 dB, ratio 1:4, range ~6–12 dB rather than full mute). Zero latency (no look-ahead).
4. **[Optional, latent] Pitch correction** — first in the tonal chain, on the cleanest signal, before saturation (hard-tune chains put the tuner first, then delay and reverb). Bypassed = zero latency.
5. **De-esser A** (split-band, detector 5–8 kHz; default light) before compression, so compressors do not exaggerate sibilance.
6. **Corrective EQ** (low-mid cut 250–400 Hz, any notch).
7. **Compressor A — fast "FET" peak control** (4:1–8:1, fast attack, 3–6 dB on peaks).
8. **Compressor B — slow "opto" levelling** (soft knee, 2–3 dB average). Two gentle stages are the documented norm (SOS two-stage; FET→opto).
9. **Tone EQ** (presence 2.5–4.5 kHz, air shelf 8–12 kHz) after compression so the compressor does not undo it; optional **De-esser B** set light after the air boost (the "boost then de-ess" approach).
10. **Saturation** (type per preset; with a parallel mix control so "parallel distortion" is one knob).
11. **Width / doubler / chorus** (mono→stereo happens here; wet-only modulated delays so the dry centre stays undelayed).
12. **Sends, post-everything:** Delay (tempo-synced or ms; HPF/LPF and tape colour on the return; optional duck) → feeds Reverb (pre-delay; return HPF 200–600 Hz, LPF 5–10 kHz; optional duck ≈ 3 dB keyed from the dry vocal). Delay return can also feed the reverb.
13. **Output:** safety limiter/soft clip (no look-ahead in monitor mode) and automatic make-up so presets are loudness-matched.

Everything except step 4 can run with zero added latency (minimum-phase IIR filters, feed-forward detectors without look-ahead, memoryless shapers; if the saturator is oversampled, use minimum-phase/IIR resampling or accept and state the sub-millisecond delay).

#### 3.7 Simple-control mapping (one-knob macros, in the spirit of Nectar's "intent" controls)
- **Clean-up** (HPF frequency + gate depth), **Tone** (tilt between warmth and air), **Presence**, **Compress** (lowers both thresholds relative to the auto-levelled −18 dBFS; display total GR), **De-ess**, **Drive** (saturation amount with auto level compensation), **Space** (reverb send + decay scaling), **Echo** (delay send + feedback), **Width**. Tempo-aware defaults: delay times and reverb pre-delay derived from the song tempo the app already holds (pre-delay = 1/64 or 1/32 note clamped to 20–120 ms).

#### 3.9 Other design inferences
- The EQ-before/after-compression debate is best resolved structurally (corrective cuts before, tonal boosts after), which is what the two documented chains do between them (SOS: comp → EQ; hip-hop bus: EQ boost → de-ess → comp).
- Because de-essing is threshold-based, it must sit *after* auto-level and before any user "output" or fader automation, and effect sends should be taken post-de-esser (documented failure mode in the metal articles).
- Feeding the delay return into the reverb (documented twice) is a cheap way to make one reverb glue both; a strip can hard-wire a "delay → reverb" amount.
- A 3 dB ducker with 250–500 ms time constants on the reverb return and a 2:1/150 ms compressor on the delay return, both keyed from the dry vocal, are small, zero-latency additions that noticeably improve clarity in dense presets (#1, #5, #10, #12).
