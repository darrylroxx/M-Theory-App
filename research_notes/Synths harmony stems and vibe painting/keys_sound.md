## Q1. Open sampled pianos, file formats, sample spacing and pitch-shift range, release/pedal/resonance, loudness

### Takeaway
The best open acoustic pianos are Salamander Grand V3 (CC BY 3.0; 48 kHz/24-bit; 30 pitches every minor third x 16 velocity layers; 748 MB FLAC), Headroom Piano (Yamaha C3, CC BY 4.0; minor thirds x 5 layers x 2 mics; 156 MB FLAC) and the VCSL Steinway B / Kawai grands (CC0; whole-tone or minor-third spacing, 3-4 layers). Trimmed to 30 pitches x 4 layers x at most 8-10 s and encoded as Opus at about 96 kb/s, a high-quality piano is 12-15 MiB to download. The real limit is decoded RAM (329-393 MB at 48 kHz stereo float32), so lazy decoding is required. Minor-third sampling (shifts of 1-1.5 semitones) is the norm in every open set checked, and measured errors at that spacing are smaller than the natural note-to-note variation.

#### Source detail: Pitch-shift experiment (my measurement, Salamander v8 C4, D#4, F#4 at 48 kHz, mono sum; script scratchpad pshift.py)
- [CALC] Linear-interpolation resampling error vs an ideal band-limited (FFT) resample of C4, first 1 s: +1 semitone 58.4 dB SNR, +3: 60.6 dB, +6: 54.0 dB, +12: 82.4 dB -> Chromium's linear interpolator is not the limiting factor for piano (piano has little energy near Nyquist).
- [CALC] Decay realism: time to fall 40 dB (50 ms RMS) - real C4 9.2 s, real D#4 5.85 s, C4 shifted +3 = 7.75 s, F#4 shifted -3 = 8.45 s, seam C4+1.5 vs D#4-1.5 = 8.45 vs 6.35 s. Note-to-note variation of a real piano (C4 vs D#4: 9.2 vs 5.85 s) is already as large as the error from shifting 1.5-3 semitones, so minor-third sampling (+-1 or +-1.5 semitone shift) is perceptually safe; the 1/3-octave envelope metric I tried was dominated by partial placement (real C4 vs real D#4 differ 9.3 dB mean) and is not informative.
- [SEC/inference] Shifting changes the decay rate and the spectral envelope (formants of soundboard/hammer move with the shift) by the same ratio as pitch; at +-1.5 semitones that is a 9% change; at +-3 semitones (sampling every 6 semitones) 19%.

### Inferences
- Minor-third spacing (as in Salamander and Headroom) is the right density: whole-tone (VCSL Steinway) is better but costs 1.5x the files; major-third spacing (+-2 semitones) is acceptable for a smaller "lite" set, and +-3 or more starts to change decay and timbre noticeably (19% rate change at 3 semitones).
- 4 velocity layers is the sweet spot for a songwriting app: Salamander's 16 are overkill, and with 1-2 layers dynamics become a filter or gain effect only (smplr's PPP layer = PP + 1 kHz lowpass).
- Do not loudness-normalise per layer. Apply one gain to the whole instrument (for example C4 mf at about -18 LUFS short-term), and use a velocity-to-gain curve (veltrack 0.7-0.75) on top.
- Release noises (88 files, 5.6 MB) and the 3-layer string-resonance releases (14 MB) are cheap. Adding them plus a pedal-down octave-resonance voice gives most of the realism that commercial players add.

## Q2. Modelled pianos in open code (Faust, waveguide, modal) - quality, CPU, realism in a browser

### Takeaway
The open modelled pianos available are a commuted-waveguide piano from STK (MIT-style, in Faust) and a new Faust port of C. Otey's 2007 waveguide+FDN piano (no licence, so reference only). They are cheap enough for a browser AudioWorklet, but by common judgement [SEC] they sound clearly synthetic next to a multi-sampled grand. Use modelling only for a "lite/no-download" fallback or for resonance effects, not as the main acoustic piano.

### Inferences
- Damper logic to implement: on note-off with the pedal down, mark the voice "held". On pedal-up, release all held voices (as mda does with its SUSTAIN marker). Re-striking the same key chokes the previous voice with a 30-100 ms fade, as Salamander's note_polyphony=1 / off_time 0.5 does.
- Release samples: on note-off (or pedal-up), start the rel<N> hammer sample at -37 dB x velocity factor and, for vel >= 45, the harm string-resonance release at -4 dB. Scale both by the elapsed time since note-on (rt_decay 2-7 dB/s in the SFZ).
- Lazy loading: fetch and decode per (pitch-zone, layer) when first needed, starting with the layer nearest velocity 80 across all 30 pitches (about 3 MiB Opus, about 80 MB decoded at 8 s / 48 kHz). Fill other layers in the background, with an LRU cap (for example 200 MB) that evicts unused layers. Use "nearest loaded layer" as a fallback while loading.
- Memory saving: decode in an OfflineAudioContext at 32 kHz (Chromium resamples on playback), which cuts RAM by 33% with no audible loss for a piano.
- Offline WAV export: build the same graph in an OfflineAudioContext with the same buffers (AudioBuffers can be shared between contexts at the same sample rate), schedule all notes, then startRendering(). smplr's renderOffline shows the pattern. The app already has src/audio/wav.ts.

## Q5. Distribution: bundle vs download on first use, integrity, cache location (PWA Cache Storage, Tauri app data)

### Takeaway
Ship a small set inside the app (mda ePiano data, organ and FM are synthesised, plus optionally a 3-4 MiB "lite" piano layer). Download the full piano pack (12-15 MiB Opus) on first use. In Tauri, download it from a GitHub release asset in Rust, check SHA-256, and store it under app_data_dir. In the PWA, serve the pack from the PWA's own origin (GitHub release assets send no CORS headers), store it in a dedicated Cache Storage cache and request navigator.storage.persist(). The current service worker would delete a separate sample cache on update, so it must be changed first.

### Cited Findings

### Inferences
- Pack format: one manifest JSON (version, licence/attribution text, per-file name, pitch, velocity range, gain, loop/trim, SHA-256, bytes) plus Opus files, or one concatenated binary blob with offsets so that one request and one hash cover everything. ## Q6. Recommendation

### Takeaway
Acoustic piano: Salamander Grand V3, reduced to 30 pitches (every minor third, shifts of at most 1 semitone) x 4 velocity layers (v4, v8, v12, v16; or v3/v7/v11/v15), trimmed to at most 10 s (8 s above C5, with a 0.5-1 s fade), 48 kHz stereo Opus at 96 kb/s VBR. That is about 12.4-14.8 MiB, plus the 88 hammer-release samples and 23 string-resonance releases (about 2-3 MiB as Opus), for about 15-18 MiB total. Ship an AAC 128k copy for WebKit (about 1.3x the size). For a CC0 alternative with no attribution, use VCSL Kawai (minor thirds, 4 layers) or Steinway B (whole tones, 3 layers) at the same budget. Headroom (CC BY 4.0) is the safest CC BY choice for GPLv3 compatibility. Electric piano: port mda ePiano (MIT/GPL-2+), add an FM E.PIANO-style voice using MSFA math, and optionally Greg Sullivan's Wurlitzer (CC BY 3.0). Organ: synthesise from the setBfree constants (GPL-2+). The expected quality is clearly above the GM-soundfont level and close to entry-level commercial players. The main losses are the high-dynamic nuance of 16 layers and tails shorter than 10 s in the bass (fine for songwriting, audible on long, exposed held chords).

### Inferences
- Implementation outline: (1) an offline Node/ffmpeg script in /scripts picks files, trims with a fade, measures one global gain, encodes Opus 96k plus AAC 128k, and writes the manifest with SHA-256. (2) A sampler engine in src/audio (AudioBufferSourceNode per voice -> per-voice gain envelope -> optional lowpass for velocity brightness -> instrument bus) with zones keycenter +-1, velocity crossfade optional, note choke, damper hold, release samples, pedal-down octave-resonance voice (-11 dB, 0.1 s attack) and voice cap of about 64. (3) Lazy decode at 32 kHz with an LRU cap. (4) The same engine in an OfflineAudioContext for WAV export.
- CPU [inference]: the sample path costs one buffer source + gain (+ biquad) per voice, so 64 voices is trivial in Chromium. The organ and FM voices belong in one AudioWorklet each.
